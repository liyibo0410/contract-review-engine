# 交付物总览

本文档汇总本次 1.0 版本交付的**全部产物**，并逐项说明其与原始需求资产、验收标准之间的对应关系。
细粒度数字以 `verify/stats.txt` 为准，验证结果以 `verify/*.txt` 为准。

## 一、交付物清单

### 1. 可运行程序

| 文件 | 说明 |
| --- | --- |
| `run.py` | 启动入口：配置加载、数据初始化、模拟审批系统初始化、打印访问地址；支持 `--port` / `--reset` / `--selftest` |
| `app/config.py` | 配置加载与路径解析（相对路径统一基于项目根） |
| `app/store.py` | SQLite 持久层（5 张表）+ 任务状态机 + 审计写入 + 大盘统计 |
| `app/parsers.py` | 文档解析引擎：格式探测、DOCX（OOXML 直解）、PDF（对象扫描 + 滤镜链 + ToUnicode CMap） |
| `app/ocr_win.py` | 扫描件 OCR 通道（Windows 内置 OCR），含 OCR 文本规整与置信度评估 |
| `app/review.py` | 条款切分、元数据抽取、规则引擎（5 种匹配模式）、条款推荐、结论判定 |
| `app/llm.py` | 大模型接入（可选，仅润色中文摘要，失败自动回退规则模板） |
| `app/notify.py` | **按需通知**：钉钉机器人 / 通用 Webhook，后台异步投递 + 加签 + 防抖 + 失败隔离 |
| `app/output.py` | 审查意见撰写、报告导出（Markdown / HTML / PDF 三通道） |
| `app/writeback.py` | 审批回写模块：幂等检查、预览模式、失败落库、重试 |
| `app/pipeline.py` | 审查流水线编排与详情聚合 |
| `app/server.py` | HTTP 服务与路由（标准库 `ThreadingHTTPServer`） |

### ⚠️ 需要确认的一点：验收标准截图内容不匹配

对 `验收标准.png` 做文字识别后的结果是：

> 2·11·10 验收标准
> · 能通过账号密码正常登录系统，支持根据民警身份及机构展示对应功能与数据
> · 能在笔录列表查看全部笔录记录，支持关键字检索、状态快速筛选、长文本摘要悬浮查看与分页导航
> · ……（问询提纲、五流证据覆盖状态、DOCX 笔录文书下载等）

这属于 **2.11 智能问询笔录平台**的验收标准，不是 2.4 合同审批审查系统的。
而同一批资产里的 `项目导航.png` 截图恰恰是「2.4 合同审批审查系统」的目录——
推测是**截取时取错了页**。

**本交付物的处理方式**：以需求基线（`项目实战.md` 2.4.10）中的 8 条验收标准为准，
并在 `docs/验收对照表.md` 中逐条对照；同时保留 `验收标准.png` 原件与 OCR 文本作为留档。
如该截图另有含义（例如需要参考它的表述粒度与验收语气来细化本合同审批项目的验收标准），
可据此再做一版更细的验收条目——**这一项请你确认**。

### 6.1 修复的缺陷

#### ① 配置错误：6 项配置写了但代码从不读取（配置漂移）

| 配置项 | 原状况 | 处理 |
| --- | --- | --- |
| `review.min_text_chars` | 定义在配置里，解析层硬编码 `30` | 真正接入解析链路（PDF / DOCX / OCR 三处共用） |
| `review.ocr_min_confidence` | 从未被读取 | 接入 OCR 判定：低于阈值判为需人工复核并给出具体原因 |
| `review.block_on_parse_fail` | 从未被读取 | 关闭时改为「降级继续审查」而不是直接阻塞 |
| `approval.base_url` | 硬编码 `127.0.0.1:8770` | 留空即由服务端按实际监听端口自动填充（换端口不再错位） |
| `approval.app_id` | 无用途 | 作为回写评论的来源系统标识写入审计与请求体 |
| `mock.seed` | 无用途 | 控制是否用示例集播种模拟审批待办（对接真实平台时可关闭） |

同时**删除了语义重复的 `dry_run_default`**（与 `write_mode` 冲突），并把 `app/config.py`
重写为「集中默认值 + 按 `_SCHEMA` 逐项校验类型与取值范围 + 非法值回退并暴露到
`/api/health` 的 `config_warnings`」，避免带着坏配置静默启动。

#### ② 安全边界：5 处可被绕过的入口

| 问题 | 风险 | 修复 |
| --- | --- | --- |
| 上传只在前端限制大小，服务端无校验 | 构造请求可上传任意大文件打爆内存 | `review.max_upload_mb` 服务端强制，超限返回 400 |
| 文件名未做路径穿越处理 | `../../x` 类文件名可能写到上传目录之外 | `safe_name()` 只取 basename、剔除隐藏名、限制长度 |
| `update_case/update_result` 直接按传入字段拼 SQL | 误传字段即报错，存在注入面 | 字段白名单，未登记字段忽略并记审计 |
| `/api/cases/{id}/opinion` 对不存在案件返回 200 | 前端误以为保存成功 | 改为 404 |
| `/api/config` 若照搬配置会泄露 Webhook 与密钥 | 凭据泄露 | 只暴露非敏感项；通知状态里 Webhook 做 `access_token=***` 脱敏 |

#### ③ 逻辑缺陷：7 处

1. **前端原文高亮被触发两次** —— `<mark>` 上同时有内联 `onclick` 和 `renderDoc()` 里追加的
   `addEventListener`，`pick()` 会执行两遍（重复滚动/闪烁）。改为只保留内联绑定，另补键盘可达性。
2. **备选方案替换依赖 DOM 层级** —— 用 `btn.parentElement.querySelector('.quote')` 取文本，
   DOM 稍变即失效。改为 `data-alt` 属性传值。
3. **批量审查静默吞异常** —— `catch (e) {}` 导致失败无感知。改为汇总失败数与原因并提示。
4. **法务批注无长度上限** —— 补齐 20000 字上限并返回 400。
5. **`/api/metrics` 用了闭包变量 `app` 而非 `self`** —— `NameError` 被全局异常处理兜成 500。
   这是新增代码自身的缺陷，在冒烟测试中当场暴露并修正。
6. **整库重置不彻底** —— `?full=1` 未复位 `sqlite_sequence`（案件 ID 不从 1 开始），
   也未清理解析缓存，旧段落树残留。已补齐。
7. **规则库写坏正则会静默失效** —— 规则支持在线编辑，一条 `(未闭合` 会让该规则永远不命中却无人知晓。
   现在：跳过该规则 + 写入 `rule_diag` + 随详情接口暴露 + 工作台顶部告警 + 规则页保存前校验并拦截。

#### ④ 性能瓶颈：6 处

| 问题 | 原实现 | 优化后 | 实测 |
| --- | --- | --- | --- |
| 规则引擎重复计算 | 每条规则 × 每个段落 × 每个表达式都重算一次「去空格文本」并重新编译正则 | 单次 `run_rules` 内按段落缓存去空格文本，正则预编译复用 | 400 段合同 × 12 条规则单次 **6 ms** |
| 大响应未压缩 | 详情接口含整篇正文，动辄数百 KB | ≥1KB 文本响应 gzip，按 `Accept-Encoding` 协商并设 `Vary` | 详情响应压到 **8 KB 级** |
| 解析结果每次读盘 | 详情页每次 `json.load` 整份解析文件 | 按 mtime 失效的内存缓存 + 临时文件原子替换 | 详情接口平均 ~50 ms |
| SQLite 无索引、无 WAL | 只有 2 个索引，默认 journal 模式下读写互斥 | 补齐 case_id / risk_level / 状态组合索引，开 WAL + NORMAL + busy_timeout | 并发不再 `database is locked` |
| 半开连接占用线程 | Handler 无读超时 | `timeout=30` + 关闭 Nagle | 失联连接可被回收 |
| 超长文档无上限 | 全部段落一次返回 | `max_paragraphs_expose` 截断并标记 `paragraphs_truncated` | 异常文档不打爆浏览器 |
