## 一、静态资源改 ETag 条件请求（最大的一项）

`_send()` 对所有响应一律发 `Cache-Control: no-store`。对接口与页面这是**刻意的安全口径**
（含登录态与角色信息，不该落盘），但对 `/assets/*` 只是纯浪费。

实测一次导航要请求的静态资源合计 **44.7 KB**（app.css 16.0 + logo 11.5 + app.js 10.8 + fx.css 6.7）。

| 资源 | 策略 | 依据 |
| --- | --- | --- |
| `/assets/*` | `Cache-Control: no-cache, must-revalidate` + `ETag`（弱校验 `W/"mtime-size"`），命中 `If-None-Match` 回 **304 空响应** | 公开资源；文件名无内容指纹 → 不适合长缓存，但非常适合「存下来、每次问一句」 |
| 页面 HTML | **保持 `no-store`** | 含登录态/角色信息，安全口径不放松 |
| 接口 JSON | **保持 `no-store`** | 实时数据，且不该落盘 |

### 为什么用 `no-cache` 而不是 `max-age`

这些文件名没有内容指纹，`max-age` 长缓存会在**重新部署后让旧 CSS/JS 粘在浏览器里**，
很难向使用者解释。`no-cache` 的语义是「可以存，但每次必须问一句」——
命中时回 304 空响应，**省掉的正是整个响应体**，而且永远不会过期失真。

若将来要做 `max-age` 长缓存，前置条件是先引入内容指纹（URL 加 `?v=`）。

### 顺带修掉一个「会静默失效」的写法

`_send()` 原本无条件写 `Cache-Control: no-store`。若只是把可缓存策略塞进 `extra_headers`，
响应里会出现**两个 `Cache-Control` 头**，浏览器合并后仍按 `no-store` 处理 ——
改动看着生效了，实际一点用都没有。现在改为：

```python
cache = headers.pop("Cache-Control", None) or "no-store"
```

### 效果

```
第一次访问：200，完整响应体
同一会话翻页：304，0 字节
单次翻页省 ≈ 44.7 KB
```

## 二、去掉用不到的脚本 + logo 位图瘦身

### 1. `workbench.html` 去引 `charts.js`

先核对再动手：全站只有 `index.html`（`CH.donut` / `CH.hbars`）与 `rules.html`（`CH.hbars`）
用到图表 API，`workbench.html` **一处 `CH.*` 都没有**。去掉后该页请求数 9 → 8，省 4.5 KB。

> 为什么不能靠「看着像」判断：`charts.js` 还导出了 `clock` / `pipeline` / `walk` 等工具，
> 容易误以为别的页面在用。**判断依据必须是真实的调用点，不是文件里有什么。**

### 2. logo 位图瘦身

| | 位图 | 显示尺寸 | 体积 |
| --- | --- | --- | --- |
| 优化前 | 125×128 | 顶栏 26×27 ｜ 登录页 38×39 | 23.3 KB（深浅两套各一份） |
| 优化后 | **76×78** | 同上 | **11.5 KB（省 51%）** |

76×78 = 最大显示尺寸 38×39 的 **2 倍**，任何场景都不会被放大 → 不存在变糊的路径。

### 视觉验证不靠肉眼

1. 用无头浏览器在 `deviceScaleFactor=2` 下截出 logo 区域（优化前 / 优化后各一张）；
2. 逐像素比对：**平均差 1.34/255，>32 亮度差的像素占 0.079%**（全部落在边缘抗锯齿上）。

**中途纠了一次自己的口径错误**：第一版把两张裁图**各自再缩一次**到显示尺寸再比，
测出 0.60% 超标 —— 那是**二次重采样的相位差**，不是画质损失。
正确判据是浏览器自己的渲染结果（2x 裁图直接比）。

原图备份在工作区 `.workbuddy/_logo_orig/`（不随交付物走）。

## 三、圆角族收敛：同族元素不再各写一个值

「圆角 20 种」这个数字**本身不是问题** —— 药丸 `999px`、圆形 `50%`、微元素 `2–6px`
本来就该不同。真正让人「看着不齐」的是**同族元素各写一个值**：

```
卡片/面板族：.panel 12px ｜ .risk-card 10px ｜ .kv-cell 11px ｜ .mode-col 13px
             .modal 14px ｜ .model-card 10px ｜ .store-card 10px ｜ .toast 10px …
图标底/小底板族：.kpi .ic 9px ｜ .panel-head .t .ic 7px ｜ .store-card .si 6px
             .donut-legend .lg 6px ｜ .dash-head .dh-logo 10px …
```

`tools/fix_radius_tokens.py` 按「选择器 → 目标值」**精确改写**（只动 `border-radius` 值，
不碰其它属性），共 **23 处，全部在 ±2px 内**，收敛到两个令牌：

- 卡片/面板/浮层 → `var(--radius)`
- 图标底/开关/导航项/日志条目 → `var(--radius-s)`

### 判据写在浏览器计算值上

刻意不数源码里的「不同写法个数」（那个数会被合理差异污染），而是逐页问浏览器：
`getComputedStyle(el).borderTopLeftRadius`，**深/浅两个主题各一遍**：

```
卡片/面板族  70 个元素 → 深色 14px ｜ 浅色 14px   （各只剩 1 个取值）
小底板族    110 个元素 → 深色  9px ｜ 浅色  9px   （各只剩 1 个取值）
```

### 顺带清掉一个「死值」

`--radius/--radius-s` 在文件**前半段**的 `:root` 里写着 `12px/8px`，但**后半段**
「v2.0.1 配色重定」的 `:root` 又声明了 `14px/9px` —— 后者生效，**前者完全是死值**。

它会让人（本轮就让我自己）误判实际圆角。已删除并留注释指向生效处，实测计算值不变（仍 14/9px）。

探针也加了对应检查，但**只看顶层 `:root` 块之间的重复** ——
`html[data-theme="light"]` 里的同名变量是**正常的主题机制**，不是死值（这个区分不做，
检查就会变成一个天天误报的噪音源）。
