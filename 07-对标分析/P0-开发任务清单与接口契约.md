## 1. 领域模型

六个核心对象。**字段名一旦定下就不要再改**，前端与规则配置全依赖它。

### 1.1 `Anchor` 锚点协议 ★ 最优先

```jsonc
{
  "block_id": "blk_0002_0012",     // 全局唯一，doc_id 内序号，与 ClauseBlock 一比一
  "page": 7,                        // 首段所在页，从 1 开始
  "para_index": 12,                 // 该页内段落序号（DOCX 用全文段落序号）
  "char_start": 4310,               // 在「归一化全文」中的字符偏移（左闭）
  "char_end": 4372,                 // 右开
  "bboxes": [                       // 归一化坐标 0~1，相对页面左上角；跨页/换行可多段
    { "page": 7, "rect": [0.132, 0.418, 0.876, 0.452] }
  ],
  "source": "pdf_text"              // docx | pdf_text | ocr
}
```

**三条链路怎么拿 bbox：**

| 载体 | 方式 |
|---|---|
| `pdf_text` | 文本抽取器输出 `Tj` 时同步记录文本矩阵（`Tm`/`Td`），把 4 个角点经 CTM 变换到设备空间，再除以页宽高归一化 |
| `docx` | 后端**只给**`para_index`，`bboxes` 由前端渲染后 `getBoundingClientRect()` 相对页面容器反算并回填缓存 |
| `ocr` | `OcrLine.Words[].BoundingRect`（像素）÷ 位图宽高 |

**硬约束：**
1. `char_start/char_end` 是**归一化全文**的偏移。归一化全文 = 解析器输出的纯文本，块之间以单个 `\n` 连接。**不要**用原始文件字节偏移。
2. `bboxes` 至少 1 段；跨页条款必须产出多段（这是"跨页条款只亮一半"的根因）。
3. **前端禁止任何基于 `indexOf` / `Range` 的文本搜索定位**——重复条款、PDF 抽取的空格差异、分页断裂都会让它错位。

**前端渲染契约：**
- 页面容器 `position: relative`，覆盖层 `position: absolute; inset: 0; pointer-events: none`，每个 bbox 一个子元素
- 配色：`high` 填充 `#E24B4A` α0.22 + 1px 实线边框 ｜ `medium` `#BA7517` ｜ `low` `#888780`
- 同一位置多框重叠：按最高等级取色，右上角加小圆点 + 数字
- 卡片 → 原文：`scrollIntoView({block:'center', behavior:'smooth'})` + 覆盖框 300ms 脉冲（`outline` 动画）
- 原文 → 卡片：hover 覆盖框高亮对应卡片；点击滚动风险面板到卡片位置

### 1.3 `Risk` 风险项

```jsonc
{
  "risk_id": "RK-0002-007",
  "task_id": "T-2026-0918-002",
  "source_type": "deterministic",    // ★ deterministic | semantic | external
  "level": "high",
  "title": "付款比例合计不等于 100%",
  "dimension": "金额支付",
  "clause_type": "付款方式与节点",
  "anchor": { "...": "见 1.1" },

  "rule_id": "D-02",
  "rule_hit": "sum_ratio=0.95, nodes=3",       // 命中的具体证据，界面展示

  "legal_basis": [                              // 语义/外部类必填；确定性类可选
    { "code": "民法典", "article": "第五百八十五条", "verified": true }
  ],
  "llm_reasoning": null,                        // deterministic 类恒为 null
  "confidence": null,                           // deterministic 类恒为 null（界面不显示）
  "external_evidence": null,                    // external 类填 {data_source, queried_at, raw}

  "suggestion": {
    "text": "将各付款节点比例调整为 30% / 65% / 5%，合计 100%。",
    "template_id": "C-PAY-001",
    "adopt_status": "pending",                  // pending | accepted | edited | rejected | not_a_risk
    "edited_text": null,
    "edit_reason": null,                        // 措辞不当 | 口径不符 | 过于保守 | 条款不适配
    "updated_by": null,
    "updated_at": null
  },
  "created_at": "2026-09-18T23:00:00+08:00"
}
```

**三类来源的界面差异（必须实现，这是可信度分层）：**

| `source_type` | 卡片底部展示 | 配色标识 |
|---|---|---|
| `deterministic` | `命中 D-02 ｜ 确定` | 左侧色条实心 |
| `semantic` | `命中 R-IP-001 ｜ 民法典第 847 条 ｜ 置信度 91%`（条文可点开） | 左侧色条 + 斜纹 |
| `external` | `来源 mock-gsxt ｜ 查询于 2026-09-18 22:41` | 左侧色条 + 数据源图标位 |

### 1.4 `ReviewTask` 任务 + **双状态机**

```jsonc
{
  "task_id": "T-2026-0918-002",
  "contract_name": "软件采购合同",
  "contract_no": "YS-2026-CG-047",
  "applicant": "王一鸣",
  "dept": "信息技术部",
  "business_type": "采购",                 // 采购 | 销售 | 服务 | 劳动（可由系统自动识别）

  "amount": { "value": 280000.00, "currency": "CNY", "in_words": "贰拾捌万元整" },
  "counterparty": {
    "name": "云枢软件技术有限公司",
    "credit_code": "91440300MA5F8G2H4K",
    "verify_status": "normal",            // normal | warning | abnormal | unverified
    "verified_at": "2026-09-18T22:41:00+08:00"
  },

  "documents": [
    { "doc_id": "doc_0002", "stage": "draft",  "filename": "...docx", "format": "docx", "pages": 9, "parse_status": "ok" },
    { "doc_id": "doc_0009", "stage": "signed", "filename": "...pdf",  "format": "pdf",  "pages": 9, "parse_status": "ok" }
  ],

  "status": "reviewing",                  // pending | parsing | reviewing | blocked | completed
  "blocked_reason": null,
  "last_error": null,

  "writeback_status": "not_written",      // not_written | writing | success | failed
  "report_version": 1,                    // 每次结论内容变化自增，参与幂等键

  "overall_risk": {
    "grade": "high",
    "score": 75.5,
    "vetoed": true,
    "veto_reason": "无验收前置条件的全额付款",
    "breakdown": { "max_item": 40.0, "high_count": 12.5, "density": 20.0, "exposure": 3.0 }
  },

  "snapshot_id": "SN-0002-01",
  "created_at": "2026-09-18T22:35:00+08:00",
  "updated_at": "2026-09-18T22:41:12+08:00"
}
```

**状态机（两个独立字段，绝不能合并）：**

```
task.status:       pending ──► parsing ──► reviewing ──► completed
                                  │            │
                                  └──► blocked ◄┘        blocked ──(retry)──► parsing

writeback.status:  not_written ──► writing ──► success
                                      └──► failed ──(retry)──► writing
```

- `blocked` 触发条件：文档加密 / OCR 严重模糊 / 正文为空或有效条款不足 / 解析置信度过低
- `writeback.failed` **不得**把 `task.status` 改成 `blocked`；两者独立重试
- 所有状态变更写 `status_history`（from / to / at / by / reason），界面渲染为时间轴

### 1.5 `ReviewSnapshot` 审查快照（可复现）

```jsonc
{
  "snapshot_id": "SN-0002-01",
  "task_id": "T-2026-0918-002",
  "rules_version": "v1.1.0",
  "prompt_version": "p2",
  "model": "deepseek-chat",
  "temperature": 0,
  "splitter_version": "s1.1",
  "input_hash": "sha256:9f2c...",          // 归一化全文 + stage=draft 的哈希
  "parsed_at": "2026-09-18T22:36:01+08:00",
  "reviewed_at": "2026-09-18T22:41:00+08:00"
}
```

**缓存键** = `input_hash + rules_version + prompt_version + model + temperature + splitter_version`。命中缓存直接返回历史结果并标注「复现（缓存命中）」。

### 1.6 `Rule` 规则（统一三类）

```jsonc
{
  "rule_id": "D-02",
  "name": "付款比例合计不等于 100%",
  "source_type": "deterministic",     // deterministic | semantic | external
  "dimension": "金额支付",
  "contract_types": ["采购", "销售", "服务"],
  "risk_level": "high",
  "detect": {
    "mode": "deterministic",           // deterministic | pattern+semantic | semantic | external
    "checker": "payment_ratio_sum",    // deterministic 类必填：注册到 CHECKERS 表的纯函数名
    "params": { "...": "" }
  },
  "veto": false,                       // true 时命中即判高风险
  "enabled": true,
  "version": "1.0",
  "status": "active",                  // draft | active | deprecated
  "effective_from": "2026-09-18",
  "effective_to": null,

  "stats": {                           // 由审查结果回写，大盘「规则健康度」用
    "hit_count": 27,
    "false_positive_count": 1,
    "suggestion_shown": 27,
    "suggestion_accepted": 18
  }
}
```

> ⚠️ **误报率与建议采纳率是两个独立指标**，不要合成一个"准确率"。误报 = 法务点了"这不是风险"；不采纳 = 法务认可判定但不用这个改法。

## 2. 接口契约

统一约定：
- 前缀 `/api`，JSON 收发，UTF-8
- 时间一律 ISO 8601 带时区（`+08:00`）
- 金额一律用字符串小数（避免浮点），如 `"280000.00"`
- 错误体：`{ "error": { "code": "TASK_NOT_FOUND", "message": "..." } }`
- 列表统一 `{ "items": [], "total": 0, "page": 1, "size": 20 }`

### 2.1 任务与文档

**`POST /api/tasks`** 创建审查任务（上传合同）
```jsonc
// multipart/form-data: file, contract_name?, business_type?, applicant?, dept?
// → 201
{ "task_id": "T-2026-0918-002", "status": "parsing" }
```
- 同名同哈希文件已存在 → 返回 200 + 已有 `task_id`（去重）
- 单文件上限 30MB，超 50 页的扫描件在解析阶段自动降级并记录

**`GET /api/tasks?status=&risk_level=&source_type=&keyword=&page=&size=`**
```jsonc
{ "items": [ { "task_id": "...", "contract_name": "...", "applicant": "...",
  "business_type": "采购", "amount": "280000.00", "status": "reviewing",
  "overall_risk": { "grade": "high", "score": 75.5 },
  "risk_counts": { "deterministic": 3, "semantic": 4, "external": 1 },
  "writeback_status": "not_written", "created_at": "..." } ],
  "total": 12, "page": 1, "size": 20 }
```

**`GET /api/tasks/{task_id}`** → 完整 `ReviewTask` + `status_history` + `snapshot` 摘要

**`POST /api/tasks/{task_id}/retry`**
```jsonc
// body: { "document_id": "doc_0002" }  // 可选，仅重试某份文档
// body: { "password": "123456" }       // 可选，加密 PDF 输入口令后重试
// → 202 { "status": "parsing" }
```
- 幂等：同一 task 在 `parsing`/`reviewing` 中重复调用返回 409 + 当前状态

**`POST /api/tasks/{task_id}/documents`** 追加文档（`stage=draft|signed`，用于双版本比对）

**`DELETE /api/tasks/{task_id}`** → 204（软删除，保留 write_log）

### 2.2 解析与条款

**`GET /api/tasks/{task_id}/document?stage=draft`**
```jsonc
{ "doc_id": "doc_0002", "format": "docx", "pages": 9,
  "pages": [
    { "page": 1, "blocks": [
      { "block_id": "blk_0002_0001", "para_index": 1, "type": "heading",
        "text": "软件采购合同", "bbox": null }
    ]}
  ],
  "full_text_hash": "sha256:9f2c...",
  "ocr_required": false, "parse_confidence": 0.96 }
```
- DOCX 的 `bbox` 为 `null`（由前端算），PDF/OCR 有值
- `full_text_hash` 与 `snapshot.input_hash` 一致，用于校验锚点是否失效

**`GET /api/tasks/{task_id}/clauses`**
```jsonc
{ "tree": [ { "block_id": "blk_0002_0001", "level": 1, "title": "第一章 总则",
    "clause_type": "主体信息", "risk_count": { "high": 0, "medium": 1 },

  "flat": [ /* ClauseBlock[] */ ],
  "coverage": { "clause_count": 11, "typed_count": 10, "low_confidence_count": 1 } }
```

**`PATCH /api/clauses/{block_id}`** 人工校正
```jsonc

{ "action": "set_type", "clause_type": "违约责任" }

```

**`GET /api/tasks/{task_id}/required-clauses`**

### 2.3 审查与风险

**`POST /api/tasks/{task_id}/review`**
```jsonc
// body: { "force": false, "reuse_cache": true }
// → 200
{ "task_id": "...", "cached": false, "elapsed_ms": 47210,
  "stage_timing": { "parse_ms": 8120, "deterministic_ms": 210, "external_ms": 640, "semantic_ms": 36020, "scoring_ms": 30 },
  "cost": { "input_tokens": 8214, "output_tokens": 1392, "estimated_cny": "0.12" },
  "risk_counts": { "deterministic": 3, "semantic": 4, "external": 1 } }
```
- 幂等：`snapshot` 未变 + 缓存命中 → 直接返回历史结果，`cached=true`
- 三段流水线：确定性校验先跑，命中 `veto` 的风险可短路跳过后续语义研判（配置开关 `short_circuit_on_veto`）

**`GET /api/tasks/{task_id}/risks?source_type=&level=&adopt_status=`**
```jsonc
{ "items": [ /* Risk[] */ ],
  "grouped": {
    "deterministic": [ /* ... */ ],
    "semantic": [ /* ... */ ],
    "external": [ /* ... */ ]
  },
  "counts": { "high": 5, "medium": 4, "low": 0 },
```

**`PATCH /api/risks/{risk_id}`**

## 3. P0 任务拆解

每项含**目标 / 产出 / 依赖 / 验收标准**。验收标准写成可执行断言，不要写成"功能正常"。

### T01 锚点协议与解析层坐标产出 ★地基

- **目标**：三条解析链路（DOCX / PDF 文本 / OCR）统一产出 `Anchor`
- **产出**：`anchor.py`（数据结构 + 校验）、`parsers/docx.py`、`parsers/pdf.py`、`parsers/ocr.py`
- **依赖**：无（最先做）
- **验收**：
  1. 样例 01/02/03/04（DOCX）→ 每个 `w:p` 产出一个 block，`char_start/char_end` 与归一化全文逐字对齐（断言：`full_text[char_start:char_end] == anchor.text`）
  2. 样例 05（纯图片 PDF）→ 走 OCR，每个 block 有 `bboxes`，`source == "ocr"`
  3. 样例 06（加密 PDF）→ 抛 `DocumentEncryptedError`，任务转 `blocked`
  4. 样例 07（空正文）→ 有效条款 < 3 → 转 `blocked`，`blocked_reason` 非空
  5. 跨页条款能产出多个 bbox（构造一份跨页样例验证）
- **坑**：`char_*` 用归一化全文偏移；DOCX 不用 `Heading` 样式时必须叠加编号正则；PDF 去 CJK 间隔空格后需用索引表映射回原坐标

### T02 前端文档视窗与 bbox 覆盖层 ★地基

- **目标**：双栏工作台，覆盖框高亮 + 与风险卡片双向联动
- **产出**：`DocumentViewer.vue/tsx`、`AnchorLayer.vue`、`useAnchorScroll.ts`
- **依赖**：T01
- **验收**：
  1. 点击任一带锚点的风险卡片 → 滚动到对应页并把覆盖框居中高亮（误差 < 1 行）
  2. 连续 10 次跳转（含同一文本重复出现的场景）不错位
  3. 跨页条款的两段 bbox 同时亮起
  4. 覆盖框 hover → 右侧对应卡片高亮；卡片点击 → 覆盖框脉冲
- **坑**：**禁止 `indexOf`/`Range` 文本搜索**；DOCX 的 bbox 需 `requestAnimationFrame` 后再算（渲染未完成会得到 0）

### T03 规则引擎内核与加载

- **目标**：统一加载三类规则，按 `contract_types` 过滤，输出 `Risk[]`
- **产出**：`rule_engine.py`、`CHECKERS` 注册表、`rules_loader.py`
- **依赖**：无（可与 T01 并行）
- **验收**：
  1. 加载 `review_rules.json`(12 R-xx) + `rules.deterministic.json`(10 D-xx + 5 E-xx) 共 27 条，无 id 重复
  2. `status != active` 或超出有效期 → 不参与审查
  3. 所有 `suggestion_clause_id` 都能在 `clause_library.json` 命中（契约测试）
  4. 规则文件语法错误 → 启动即失败并报出文件名 + 行号，不静默跳过
- **坑**：规则 DSL 不用 YAML（避免与现有 JSON 混用），直接 JSON；`checker` 名不存在时必须启动期报错

### T04 确定性校验 10 条 + 外部核验 5 条

- **目标**：实现 `D-01~D-10` 与 `E-01~E-05` 全部 checker
- **产出**：`checkers/deterministic.py`、`checkers/external.py`、`tests/test_checkers.py`
- **依赖**：T01、T03
- **验收**：
  1. 每条 checker 至少 1 正例 + 1 反例单测，全绿
  2. 单份合同全部确定性规则执行耗时 < 500ms（断言）
  3. 构造反例验证零误报：标准版样例 01 不产生任何 D-xx 风险
  4. `D-07` 占位符检测在样例 07 命中（该文件含「（待补充）」）
- **坑**：金额用 `Decimal` 不用 float；日期比较前统一解析为 `date` 对象；`D-10` 读 DOCX 要解 `w:ins/w:del/w:commentReference`，读 PDF 要判 `Annot` 与 Marked 标记

### T05 语义研判与证据链

- **目标**：R-xx 规则走 LLM，输出结构化 Risk（含条文依据 + 置信度 + 推理摘要）
- **产出**：`semantic_reviewer.py`、`prompts/review_v2.md`、`confidence.py`
- **依赖**：T01、T03
- **验收**：
  1. LLM 输出强制 JSON Schema，解析失败自动重试（最多 2 次），仍失败则该条款标 `review_failed` 而非静默丢弃
  2. `confidence` 用公式算：`0.5×规则命中强度 + 0.3×LLM 自评 + 0.2×依据可核验度`，断言结果落在 `[0,1]`
  3. 每个风险都带可点击的 `legal_basis`，且条文号能在法规库中检索到（契约测试，目标 100%）
  4. 对样例 02 跑出的风险集合与 `_预期审查结果.json` 的 6 条逐条比对（rule_id 集合一致）
- **坑**：`temperature=0`；推理摘要 ≠ 思维链，只存结论性说明；依据库缺失时要显式报错而不是编条文号

### T06 相对方核验接入与降级

- **目标**：核验 mock + 5 条外部规则的降级策略
- **产出**：`counterparty_provider.py`、`mock/gsxt_server.py`
- **依赖**：T03
- **验收**：
  1. `scenario=abnormal` → 产出 E-01 且 `vetoed=true`，`task.status` **不变**为 blocked
  2. `scenario=timeout` → 3 秒超时 → 产出「核验未完成」中风险 → 审查流程继续完成（不阻塞）
  3. 核验结果带 `queried_at` 与 `data_source`，缓存 24h 内复用但时间戳原样展示
  4. 劳动类合同跳过 E-xx（自然人相对方）
- **坑**：外部核验是唯一依赖第三方的环节，**任何异常都不能抛到主流程**；名称模糊匹配只能判 `mismatched` 并给出对比，不自动改判

### T07 定级算法与风险驾驶舱

- **目标**：`scoring.json` 的纯函数实现 + 大盘三张图
- **产出**：`scoring.py`、`dashboard.py`、`DashboardPage`、`ScoreBreakdown`
- **依赖**：T04、T05、T06
- **验收**：
  1. `scoring.json` 的 4 条 `test_cases_required` 全部实现并通过
  2. 三个 `worked_examples` 的 `total` 与脚本输出一致（容差 0.01）
  3. 大盘 `overview` 全部字段可从已有数据聚合得出，无新增采集依赖
  4. `rule-health` 能报出 `silent_rules`（命中 0 次的规则）
- **坑**：`density` 在条款数 < 5 时跳过并置 `density_skipped=true`；`veto` 命中时仍照常算 score 供参考，但结论用 veto

### T08 回写闭环（幂等 + 日志 + 时间轴）

- **目标**：可靠回写，可重试、可追溯、不重复
- **产出**：`writeback.py`、`write_log` 表、`WritebackPanel`
- **依赖**：T07
- **验收**：
  1. 同 `Idempotency-Key` 连续请求 5 次 → mock 侧评论数 == 1，5 次响应的 `comment_id` 相同
  2. 缺 `Idempotency-Key` → 400
  3. `mode=500` 故障注入 → `writeback_status=failed`，`task.status` **保持 completed**
  4. 点重试 → `attempt=2`，成功后 `logs` 有两条记录
  5. 界面时间轴 `not_written → writing → success/failed` 节点带时间戳与耗时
- **坑**：`report_version` 在结论变化时自增，旧的幂等键自动失效（这是有意行为）；日志表要存完整 request/response body

### T09 条款切分质量保障

- **目标**：条款树 / 切分置信度 / 人工校正 / 必备条款空槽位
- **产出**：`clause_analyzer.py`、`ClauseTree`、`MissingClauseSlots`、`ClauseEditor`
- **依赖**：T01、T02
- **验收**：
  1. 对 7 份样例输出条款树，层级正确（章 → 条 → 款）
  2. `split_confidence < 0.6` 的段落进入「待校对」队列且界面标黄
  3. 人工 `split` 后锚点重算，`full_text[char_start:char_end]` 仍自洽（断言）
  4. 对样例 02 输出 `required-clauses`：`recognized < required_total`，缺失项渲染为空槽位卡片且可引用示范条款
  5. 覆盖率与 `_预期审查结果.json` 的条款数口径一致
- **坑**：校正后必须让 `ReviewSnapshot` 失效并提示重新审查；合同类型识别错了会导致挂错矩阵，需给「修改合同类型」入口

### T10 状态机、阻塞重试与回归基线

- **目标**：双状态机落地 + **重跑 `_预期审查结果.json` 基线**
- **产出**：`state_machine.py`、`status_history` 表、`tests/test_regression.py`、更新后的 `_预期审查结果.json`
- **依赖**：T01~T09
- **验收**：
  1. 双状态机 12 条转移路径的单测全绿（含非法转移必须抛错）
  2. 样例 06/07 → `blocked`；`POST /retry`（06 带口令 `123456`）→ 恢复流转
  3. **回归基线重跑**：对 7 份样例跑全量 27 条规则，输出实际风险计数，人工确认后更新 `_预期审查结果.json` 的 `expected_counts` 与 `expected_risk_level`，并在文件内记录基线版本号
  4. 同一输入连续跑两次 → 结果完全一致（可复现性）
- **坑**：⚠️ **这是最容易忽略的一步**。新增 10 条确定性规则后，样例 02/03 的 `expected_counts` 大概率会变（例如 D-06 条款编号、D-07 占位符、D-10 修订痕迹都可能命中）。**必须先重跑基线，再写死断言**，否则测试永远红。基线更新要单独提交，便于回溯。

## 5. 回归基线处理（必读）

**为什么必须单独说**：现有 `_预期审查结果.json` 是按 12 条 R-xx 规则标注的。本方案新增 10 条 D-xx 后，**样例的风险计数一定变**。如果直接拿旧基线写断言，测试会全红，然后就会有人去改规则来迁就测试——**方向反了**。

正确做法：

1. 实现完 D-xx / E-xx 后，写一个 `tests/rerun_baseline.py`：对 7 份样例跑全量规则，输出每份的 `rule_id → 命中` 矩阵
2. 人工逐条审阅新增命中，判断「真命中」还是「误报」：
   - 真命中 → 更新基线
   - 误报 → 收紧对应 checker 的参数（**不是**删规则）
3. 基线文件新增字段，便于回溯：
   ```jsonc
   { "baseline_version": "2026-09-18-D-v1",
     "rules_included": ["R-01..R-12", "D-01..D-10", "E-01..E-05"],
     "files": [ { "expected_counts": { "high": 2, "medium": 5, "low": 1, "by_source": { "deterministic": 3, "semantic": 3, "external": 0 } } } ] }
   ```
4. 基线更新**单独一次提交**，提交信息写明「基线变更原因」，便于日后追责与回溯

**四条不可退让的交互约定：**

1. **风险卡片按 `source_type` 分组，不按等级混排**——用户要先看到"确定"的，再看"研判"的

4. **定级必须给过程**——`ScoreBreakdown` 是常驻组件，不是 tooltip
