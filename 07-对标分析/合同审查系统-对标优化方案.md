# 合同智能审查系统 · 对标优化方案

**对标对象**：《智能合同管理平台解决方案》— 武汉楚联信息技术有限公司（致远互联 / SEEYON CoMi 生态）
**原文**：https://mp.weixin.qq.com/s/PlzVGjCZQRFcB-snMGEoVg ｜ 正文为纯图片长图，本方案基于对其 33 页 PPT 的 OCR 全文还原
**我方对象**：项目 2.4 合同审批审查系统
**日期**：2026-09-18

---

## 一、先给结论

**别去比"全生命周期"，去比"审查这一段的深度"。**

对方那份 PPT 卖的是**一个平台**：合同准备 → 起草 → 预审 → 审批 → 缔约 → 履约 → 变更 → 结项 → 归档 → 借阅，10 个环节，后面还挂着合同业务中台、智能中台、风控中台、数据中台。这是几十人年 + 已有 OA/协同办公基座才能撑起来的产品叙事。对标它做全流程，我们必输。

但它有**一块明显的软肋**：整份 PPT 里，"审查"这一环几乎没有技术细节。它讲的是"智能审查、智能比对、智能起草"三个词，然后跳到"470 万法律法规、万级范本库、1.8 亿裁判文书"这类**数据规模**，以及"知识图谱 + LLM + MOE""熊猫自研小模型"这类**架构名词**。它没有回答一个审查系统最难的问题：

- 风险点在原文的**哪个字符到哪个字符**？怎么保证高亮不漂移？
- 每条风险的**法律依据**到底是哪一条、第几款？
- 规则命中了哪条规则、置信度多少、怎么验证规则本身是对的？
- 扫描件（OCR）出来的文本，**没有字符坐标**怎么高亮？
- 回写审批单**失败了**怎么办、重复点击会不会写两条评论？

我们的 spec（2.4）恰恰把这些**都写了**——双向锚定、原文起止字符位置 + 页码 + 段落索引、规则引擎 + LLM 双判定、阻塞重试。这是我们真正的优势，**不要被那份 PPT 带偏成"我们也要做履约管理"**。

所以优化方向是三条：

1. **把"证据链"做成硬通货**（对方最缺的地方，我们做成产品标志）
2. **借它的叙事骨架**（政策锚点、角色矩阵、具体数字、智能体命名）——这些是零成本、高回报的"包装升级"
3. **补三个它强而我们弱的模块**：相对方核验、双版本一致性比对、数据驾驶舱

| 3 产品方案 | 合同门户 / 业务工作台 / 数智大屏 / 基础数据 / 风险决策 / 合同发起 / 审批 / 缔约 / 台账 / 履约全周期 | 11 个功能域，含敏感词检测、预审组、非标合同预审、电子签章、智能比对、全景台账 360 |
| 4 支撑平台 | CoMi 智能平台 + CoMi Agent + 四大中台 | 合同业务中台 / 智能中台 / 风控中台 / 数据中台 |
| 5 产品亮点 | 四个 | ①集团多级管控 ②AI 智能合同智审 ③业务集成业财一体 ④个性化扩展 |

### 2.2 它真正值得学的地方

**① 政策锚点开场，不谈功能先谈"不得不做"**
开篇就是国资厅监督〔2025〕24 号文、"以穿透式监管为主线、以智能化转型为抓手"、"全级次、全链条、全过程、全要素穿透"。这一段的价值是：让采购方觉得"不买我，你过不了检查"。我们的系统开篇全是功能清单，缺这个"为什么现在必须做"。

**② 角色 × 关注重点 × 解决方案 的三列矩阵**
它把合同业务拆成 4 个角色（业务人员 / 法务人员 / 财务人员 / 管理人员）和 4 个阶段（签订前-责任 / 签订中 / 签订后-监督 / 履约），每个交叉点写"关注重点 + 解决方案"。这东西做起来几乎不花成本，但让方案显得"懂业务"。

**③ 用具体数字讲 AI 洞察，而不是形容词**
最有力的一页是"风险洞察"示例：

> 临期事项共 **13** 项，全部集中在收类 02 与付类 0X 项，无其他类型；临期天数的跨度大（**3—331 天**），短期（≤30 天）占 **10 项**，中长期（31—90 天）占 **3 项**，远期（>90 天）占 **1 项**；XX 采购合同出现 **5 次**，为高频风险合同；……所有事项计划完成日集中在 2025 年 12 月—2026 年 10 月间，**无逾期项**，但存在集中兑付风险 2025.12.25（2 项）、2025.12.25—12.31 连续两天各 1 项。
> **建议**：优先推进 7 天内到期的"XX 线材"，确保资金及时回笼……

这段没有一个"智能""高效"之类的空词，全是可核实的数。**这是整份 PPT 里信息密度最高的一段。**

**④ 智能体矩阵命名（产品化叙事）**
合同智能中台下挂了几个有名字的 Agent：**合同守门员**（准入/主体核验）、**合同资产管家**、**合同履约达人**、**合同风险分析专家**。同一套能力，起了名字之后从"功能模块"变成了"数字员工"，报价都能高一档。

**⑤ 中台化分层**
业务中台（统一合同管理服务）/ 智能中台（智能体 + 三类模型协同：LLM + RAG/GIS + NL2SQL/API）/ 风控中台（签订前-中-后四段风控）/ 数据中台（跨平台数据流转）。分层清晰，便于讲"可扩展"。

### 2.3 它明显弱的地方

| 项 | 它的处理 | 问题 |
|---|---|---|
| 风险定位精度 | 只说"智能审查"，没有位置模型 | 无法回答"这条风险在原文哪一段" |
| 法律依据 | 只给"470 万法规"的数据规模 | 没有"这条风险依据哪条第几款"的映射 |
| 审查可测性 | 无 | 没有规则命中率/误报率，无法证明"AI 真的在干活" |
| 置信度 | 无 | 无置信度，法务不敢采纳 |
| 扫描件坐标 | 未提 | OCR 无字符坐标，高亮无法实现 |
| 回写可靠性 | 只说"自动存入档案" | 无幂等、无失败重试、无回写日志 |
| 数据规模真实性 | 470 万法规 / 1.8 亿裁判文书 | 这类数字对评审来说是"可被质疑点"，我们不必跟 |

## 四、P0 优化项（演示前必做，直接决定系统"像不像真的"）

### P0-1 统一锚点协议 Anchor Protocol ★最优先

**问题**：DOCX / PDF / OCR 三条解析链路，产出的位置信息格式不一致；前端若用"字符串搜索定位"来做高亮，遇到**重复条款文本、PDF 抽取的空格差异、跨页断裂**必然错位。这是这类系统最容易翻车、也最容易被评审一眼看穿的地方。

**方案**：定义唯一的锚点对象，解析层 → 存储层 → 裁决层 → 渲染层**共用一套坐标**。

```json
{
  "block_id": "c_0012",
  "clause_type": "违约责任",
  "page": 7,
  "para_index": 12,
  "char_start": 4310,
  "char_end": 4372,
  "bbox": [0.132, 0.418, 0.876, 0.452],
  "source": "pdf_text | docx | ocr"
}
```

`bbox` 为**归一化坐标（0~1，页面坐标系）**，PDF 原页、DOCX 渲染页、扫描件图片三种载体通用。

**三条链路的取 bbox 方式**：

| 载体 | 方式 |
|---|---|
| PDF | 自实现文本抽取器在输出 `Tj` 时同步记录文本矩阵（`Tm`/`Td` + CTM），把 4 个角点变换到设备空间再归一化 |
| DOCX | 段落级锚点（不追字级）；前端渲染 `word/document.xml` 的段落序列，按 `para_index` 定位，用 `getBoundingClientRect()` 反算 bbox 回填 |
| 扫描件 OCR | Windows `Windows.Media.Ocr` 的 `OcrLine.Words[].BoundingRect` 直接给像素框，除以图宽高归一化即可 |

**前端渲染原则**：**绝对不要"找文本"**。文档页上叠一层绝对定位的覆盖框层，按 bbox 画半透明矩形（高风险红 / 中风险琥珀 / 低风险灰），hover 与右侧风险卡片双向联动，点击覆盖框跳页。跨页、跨版本、重复文本全都免疫。

**验收**：任取一条风险，卡片 → 原文覆盖框 → 反向点击回卡片，定位误差 < 1 行；连续 10 次不错位。

### P0-2 审查证据链四元组 ★产品标志

**问题**：对方 PPT 最大的说服力缺口，就是"凭什么信你的判断"。我们把这一块做成卡片的固定结构，就是差异化的核心。

**风险卡片固定字段**：

```json
{
  "risk_id": "RK-20260918-003",
  "level": "high",
  "title": "知识产权归属供应商，我方无源程序权利",
  "clause_type": "知识产权",
  "anchor": { "...": "见 P0-1" },
  "rule_id": "R-IP-001",
  "rule_hit": "regex: 知识产权[^。；]{0,30}(归|属)乙方",
  "legal_basis": [
    { "code": "民法典", "article": "第八百四十七条", "title": "职务技术成果", "text": "……", "verified": true }
  ],
  "llm_reasoning": "该条款将定制开发成果的知识产权整体归于供应商，未保留我方对源程序、目标代码及后续改进成果的权利，与集团《软件采购合规指引》第 4.2 条冲突。",
  "confidence": 0.91,
  "suggestion": {
    "text": "建议修改为：本项目定制开发部分的知识产权归甲方所有；供应商保留其原有技术、通用组件的所有权，并授予甲方永久、不可撤销、可转授的使用许可。",
    "template_id": "T-IP-002",
    "adopt_status": "pending"
  }
}
```

**卡片底部固定一行小字**（这一行就是专业感的来源）：

> `命中 R-IP-001 · 民法典第 847 条 · 置信度 91% · 直接链接条文原文`

**置信度怎么来**（不要用模型的嘴说）：
`confidence = 0.5 × 规则命中强度 + 0.3 × LLM 自评 + 0.2 × 依据可核验度`
规则命中强度按命中类型给分（命中强正则 1.0 / 数值阈值 0.9 / 关键词弱匹配 0.6）。这样置信度是**可解释、可复现**的，不是黑盒。

### P0-3 规则 DSL + 规则回归自检

**问题**：spec 里"规则与模板管理"只给了页面，没给规则的数据结构。规则不可测 = 无法证明系统在工作。

**规则 DSL（YAML）**：

```yaml
- id: R-PAY-002
  name: 到货即付全款，无验收前置条件
  clause_type: 付款与结算
  level: high
  when:
    all:
      - regex: "(到货|交货|送达)[^。；]{0,20}(即|之日|后)?[^。；]{0,10}(全额|全款|100%)"
      - not_regex: "(验收|检测|确认合格|终验)"
  require_evidence: true
  legal_basis: ["民法典:第六百二十六条"]
  suggestion_template: "建议改为里程碑付款：预付款 30%，到货验收合格后付 60%，质保期满付 10%。"
  on_missing_anchor: "block"
  retry: { max_attempts: 2, backoff_ms: 800 }
```

**规则回归自检**（演示杀手锏）：用标注好的示例合同集跑全量规则，输出：

| 指标 | 含义 |
|---|---|
| 命中矩阵 | 规则 × 合同，命中的打点 |
| 误报率 | 人工判为"不该报"的命中数 / 总命中数 |
| 漏报率 | 人工标注的风险点未被任何规则命中数 / 总标注数 |
| 依据完整率 | 带 `legal_basis` 且条文号能在法规库中核验通过的比例（目标 100%） |

大盘页右上角放一个"**规则健康度**"小卡：`规则 24 条 · 用例 12 份 · 误报 1 · 漏报 0 · 依据完整率 100%`。
演示时一句"我们的规则做过回归验证"，比讲十句"我们接了 LLM"都有用。

### P0-4 相对方主体核验模块

**问题**：spec 的风险规则里写了"主体信息缺失或被列入经营异常 → 高风险"，但**没有任何界面和数据来源**。这是评级规则里唯一悬空的一条，评审一问就露。

**实现（轻量但完整）**：

| 项 | 做法 |
|---|---|
| 数据源 | 本地 mock：`GET /mock/gsxt/{credit_code}` → 注册状态、经营异常名录、失信被执行、成立日期、注册资本、法定代表人 |
| 内置样例 | 准备 6 条：3 条正常、1 条经营异常、1 条成立不足 1 年、1 条名称与信用代码不匹配 |
| 核验触发 | ① 从合同正文抽取的甲方/乙方名称 + 信用代码；② 与审批单申报的相对方做一致性比对 |
| 风险规则 | 名称↔代码不匹配 → 高；经营异常/失信被执行 → 高；成立 < 1 年且金额 > 100 万 → 中；未填信用代码 → 中 |
| 黑名单 | 本地表，两级（集团 / 单位），支持"申请加入黑名单"与审批状态展示 |
| 界面 | 工作台顶部"交易对手"卡 → 点开右侧抽屉：核验结论 + 命中项 + 原文主体名称的锚点跳转 |

**为什么值得做**：这是**唯一一个不依赖 LLM、纯确定性**的高风险来源，演示时能证明"系统不是只会调大模型"。

### P0-5 回写闭环：幂等 + 日志 + 状态时间轴

**问题**：spec 只有"一键回写审批单按钮"和三个回写状态，缺可靠性设计。评审很可能追问"点两下会怎样""失败了怎么办"。

**四件事**：

1. **幂等键** `idempotency_key = task_id + report_version`。重复提交返回同一个 `comment_id`，不产生第二条评论。
2. **回写日志表** `write_log(id, task_id, attempt, status, request_body, response_body, http_status, latency_ms, error, created_at)`，界面可查。
3. **状态时间轴**（回写区下方）：
   `not_written → writing → success / failed`
   每个节点带时间戳、耗时、失败原因；`failed` 节点旁边直接给"重试"按钮。
4. **回执**：mock 审批系统返回 `comment_id` + 审批单深链，界面上给"去审批单查看该评论"的入口，点击可看到评论已落库。

**关键区别**：解析 `blocked` 与回写 `failed` 是**两套状态**，不要混在一个字段里。spec 里它们是分开的，实现时也别图省事合并。

### P0-6 审查大盘 → 风险驾驶舱

**问题**：spec 的大盘页只有"待审合同列表 + 筛选 + 上传入口"。对标方的数智大屏 + 智能分析，我们的首屏没有任何"判断力"展示。

**大盘顶部指标卡（全部由现有风险卡片聚合，纯 SQL 可得）**：

| 指标 | 示例值 |
|---|---|
| 任务 | 待处理 12 · 审查中 3 · 阻塞 1 · 已完成 8 |
| 风险 | 高风险合同 4（占 33%）· 风险点合计 27 |
| 时效 | 平均审查 47s（解析 8s / 规则 3s / LLM 36s）· P95 92s |
| Top 风险类型 | 违约责任不对等 ×5 · 付款无验收前置 ×4 · 管辖地违规 ×2 |
| 条款覆盖 | 已识别条款类型 9 / 规则库覆盖 12 |
| 拦截价值 | 高风险合同金额合计 ¥1,280.00 万 |

**外加两张小图**：
- 风险热力矩阵：合同类型（采购/销售/服务/劳动）× 风险类型（主体/金额支付/违约/知产/争议管辖）
- 规则命中排行：Top 8 规则 + 命中次数（同时也暴露"哑规则"——命中 0 次的规则需要复核）

**写法要学对标方**：不要写"智能分析风险状况"，写"临期事项共 13 项，短期待办 10 项占 77%，集中于收类付款；高频风险合同为 XX 采购合同（5 次）"。

## 五、P1 优化项（拉高上限，成本可控）

### P1-1 双版本一致性比对（"阴阳合同"检测）★最具演示杀伤力

**场景**：法务审完的定稿（送审稿）↔ 用印后回传的盖章件（PDF / 扫描件）。
**价值**：对方 PPT 里明确写了这条（"智能比对：签署文本和评审文档比对一致性，防止线下传递过程中被改"），且**spec 完全没有**。实现的成本很低——解析层已有，只差一个 diff。

**流程**：
1. 同一任务下挂 `documents[]`，每个带 `stage: draft | signed`
2. 两份都过解析层 → 得到条款块列表
3. **块级对齐**：以"条款号 / 条款标题"为 key 做匹配（`第X条`、`一、`、`1.` 三类形态都归一）
4. **块内字符级 diff**：`difflib.SequenceMatcher` 取 opcodes，或前端 jsdiff 渲染
5. 输出"新增 / 删除 / 改写"三类变更块
6. **改写块自动重跑规则引擎**——若新版本引入了新的高风险项，标记为 **`suspected_tampering`（疑似篡改）**，并升到最高优先级

**界面**：左右双栏 diff，变更行红/绿底；顶部横条："检测到 3 处文本变更，其中 1 处引入新的高风险条款（违约责任上限被删除）"。

**为什么强**：这是**只有真正做过合同系统的人才想得到的功能**，一句话就能让评审记住。

---

### P1-2 合同问答智能体

**场景**：工作台右下角的输入框，问"这份合同的质保期是多久？""争议管辖地约定在哪里？"
**实现**：复用现有技术栈——
- 已切分的条款块 → 按 `clause_type` 建索引
- 向量化：直接复用现成的 **Qdrant + 本地 TEI embedding（BAAI/bge-large-zh-v1.5, localhost:8081）**，零新增依赖
- 召回 top-k 条款块 + 页码 → 拼进 prompt → 输出答案 **必须带引用锚点**
- 答案里的 `[1]` `[2]` 可点击 → 原文高亮跳转（复用 P0-1）

**注意**：答案必须**只用召回到的条款块**作答，召不到就明确说"合同中未约定"。**"承认没约定"比编一个答案更有说服力**。

---

### P1-3 付款 / 履约关键项抽取（轻量，不做全生命周期）

**问题**：spec 的高风险项之一是"未设置付款前置验收条件"，但要判这条，必须先把**付款节点**抽出来。这一步 spec 没写。

**抽取字段**：
`付款节点[]`（预付款/到货/验收/质保金 + 比例）、`账期天数`、`验收条件`、`验收期限`、`质保期`、`生效条件`、`履行期限`

**风险联动**：
- 无验收前置条件 → 高
- 预付款比例 > 30% → 中
- 质保金 < 5% 或无 → 中
- 账期 > 90 天 → 中

**可视化**：一条横向时间轴
`合同生效 → 交付 → 验收 → 付款①30% → 付款②60% → 质保期满付款③10% → 质保到期`
每个节点可点回原文锚点。

**注意**：只做"抽取 + 展示 + 联动风险"，**不做履约任务管理、不做变更结项归档**。守住"审查"这一段。

---

### P1-4 法规 / 范本 / 依据库（小规模但可核实）

**不要跟数据规模**。470 万法规对我们没有价值，反而容易被追问"数据从哪来、怎么保证时效"。

**做法**：

| 库 | 规模 | 要求 |
|---|---|---|
| 法规条文库 | 40 条（民法典合同编为主 + 招标投标法 + 数据安全法 + 劳动合同法） | JSON：`code / article / title / text / 适用场景 tags`，界面上**可点开看原文** |
| 标准条款范本库 | 12 份（付款、违约、保密、知识产权、争议管辖、不可抗力、验收、数据安全…） | 每份含"适用条款类型 + 推荐文本 + 变体" |
| 内部合规指引 | 8 条 | 标注为"企业内部规则"，与法律法规区分展示 |

**硬约束（写进测试）**：风险卡片引用的每个 `(code, article)` 必须能在法规库中检索到；法规库里的条文号不重复、不含占位符。
**演示话术**：不说"我们有 470 万条法规"，说"**每条风险建议都能点开看到依据的原文，且依据经过一致性校验**"。前者是数字，后者是可信度。

---

### P1-5 双栏整改对比报告

**问题**：spec 只说"生成并导出报告"。给业务经办人的报告如果只是风险清单，业务方不知道怎么改。

**报告第二段加"整改对比清单"**：逐条左栏原文条款、右栏建议条款、中间标 diff 高亮，末尾一列"采纳状态"（已采纳/已编辑/已驳回 + 法务批注）。业务方拿着这份就能直接改合同。

**导出**：Markdown（在线预览）+ PDF（打印版，`@page A4`、`break-inside: avoid` 防止卡片被切断、`-webkit-print-color-adjust: exact` 保证风险配色不被裁掉）。

## 七、技术落地避坑清单

| # | 坑 | 后果 | 对策 |
|---|---|---|---|
| 1 | 用"字符串搜索"定位高亮 | 重复文本、空格差异、跨页 → 全错位 | 用 bbox 覆盖层（P0-1） |
| 2 | OCR 不存 word bbox | 扫描件无法高亮，只能整段标黄 | 取 `OcrLine.Words[].BoundingRect` |
| 3 | DOCX 陷阱：很多合同不用 `Heading` 样式 | 标题识别失败、条款切分全乱 | 样式判定 **叠加**文本形态正则（`第X条`/`一、`/`1.`） |
| 4 | PDF 抽取出现"逐字空格" | 正则全部失配 | 匹配前做去 CJK 间隔空格，并用索引表映射回原坐标 |
| 5 | LLM 输出不结构化 | 偶尔返回散文，解析崩溃 | 强制 JSON Schema + 失败重试；每字段缺失即整体重试 |
| 6 | 回写无幂等 | 重复点击写两条评论 | `task_id + report_version` 作幂等键 |
| 7 | 解析 `blocked` 与回写 `failed` 混用一个状态 | 状态机死锁、无法单独重试 | 两套状态字段，独立流转（spec 已分开，实现别合并） |
| 8 | 大扫描件超时 | 单任务卡死、GPU/内存爆 | > 50 页先降采样或分片；单页超时 → `blocked` + 原因 |
| 9 | 内部自调用地址写死端口 | 换端口后 mock 全部 Connection refused | 启动时按实际监听端口重写 mock base_url |
| 10 | 规则库"哑规则" | 有条规则从来没命中过，评审一眼看出 | 大盘"规则命中排行"，命中 0 次的规则标黄待复核 |
| 11 | 法规库条文号拼错 | 卡片引用"民法典第 999 条"这种不存在的条文 | 写一条测试：所有 `legal_basis` 必须能在库中检索到 |
| 12 | PDF 中文高亮错位（分页处） | 跨页条款一半亮一半不亮 | 一个 block 允许有多个 bbox 段（`bbox[]` 数组） |

# 第二部分 · 补充优化（第二轮）

> 第一轮（一~十）对的是「**别人有什么**」——找差距、补模块。
> 这一部分对的是「**这类系统自己会漏什么、评审一定会问什么**」。
> 下面 10 项基本不是"对方有我们没有"，而是即使对方那份 PPT 也没写清楚、但真做起来绕不过去的东西。

## 十一、风险分三类来源，并对用户明示 ★

这是第一轮漏掉的**根本性设计**。spec 现在把所有风险拉平展示（高/中/低），但它们的**可信度、可解释性、处理方式完全不同**：

| 类别 | 判定方式 | 可信度 | 典型项 | 界面要求 |
|---|---|---|---|---|
| **确定性校验** | 纯规则，数值/格式/序列比对 | 几乎零误报 | 金额大小写不符、付款比例合计≠100%、日期逻辑矛盾、术语混用、编号断裂、栏位空白 | **不显示置信度**，直接标"确定" |
| **语义研判** | 规则 + LLM 语义分析 | 中等，需人工复核 | 权责不对等、必备条款缺失、管辖地违规、违约金超限、IP 归属 | 显示置信度 + 条文依据 + 推理摘要 |
| **外部核验** | 与第三方/内部数据源比对 | 权威 | 经营异常、失信被执行、名称↔信用代码不符、黑名单 | 显示数据来源 + 查询时间戳 |

**为什么这个分层比多做一个模块更重要：**

1. 用户对"系统能判什么、判不准什么"一目了然，**不会因为一条 LLM 误判就否定整个系统**
2. 演示的说服路径立刻顺了：**先摆确定性校验（"这 4 条不需要 AI，规则就能判，零误报"）建立信任，再展示 AI 的语义能力**
3. 报告可以对外说"确定性校验拦截 X 条、语义研判 X 条、外部核验 X 条"——**三个数字比一个总数可信**

**落地**：风险对象加 `source_type: deterministic | semantic | external`；卡片与报告按此分组、配色、排序（确定性优先展示）。

### 11.1 确定性校验规则清单（建议 10 条全做，成本极低、收益极高）

| # | 规则 | 判定方式 | 等级 |
|---|---|---|---|
| D-01 | 金额大小写不一致 | 抽大写（壹贰叁…）转数字，与小写金额比对 | 高 |
| D-02 | 付款比例合计 ≠ 100% | 抽出全部"XX%"付款节点求和 | 高 |
| D-03 | 日期逻辑矛盾 | 签订日>生效日 / 履行止<履行起 / 验收期>质保期 | 高 |
| D-04 | 主体名称与信用代码不符 | 与外部核验数据比对（见 P0-4） | 高 |
| D-05 | 术语混用 | 同一相对方在全文出现 ≥2 种称谓（乙方/供方/卖方） | 中 |
| D-06 | 条款编号断裂或重复 | 提取 `第X条` 序列检查连续性 | 中 |
| D-07 | 关键栏位空白 | 模板占位符未替换（`____`、`[　　]`、`XX`） | 中 |
| D-08 | 金额与审批单申报不符 | 与审批单字段比对 | 高 |
| D-09 | 期限缺失或异常 | 无履行期限 / >3 年 / 质保期 < 行业惯例 | 中 |
| D-10 | 附件清单与实体不符 | 正文提及的附件在文档中不存在 | 中 |

**这 10 条的价值**：零 token 成本、零误报、不需要 LLM，且覆盖企业真实历史事故的大部分场景。
**建议在工作台独立出一个"形式校验"tab，与"合规审查"并列**——两栏分开，用户一眼就知道哪栏是硬结论、哪栏是 AI 判断。

## 十二、条款切分的质量保障（解析层最大的隐性风险）

第一轮讲了锚点，但**没讲切错了怎么办**。实际项目里，解析层翻车比 LLM 翻车更常见：合同不用 `Heading` 样式、条款嵌套（条→款→项）、表格里藏条款、附件是另一套编号体系。

四项机制，缺一不可：

**① 条款树可视化**
左栏正文旁挂一个可折叠的条款树（章 → 条 → 款），节点标注条款类型与命中风险数（高风险红点）。这是工作台的"第二个导航"——比页码导航好用得多，也让"条款结构化切分"这件事**看得见**。

**② 切分置信度**
按「是否有样式 / 标题形态是否规范 / 段落长度 / 编号连续性」给 0~1 分。`< 0.6` 的段落标黄进"待校对"队列。这一条直接回应"你的切分准不准"。

**③ 人工校正入口**
段落支持「拆分 / 合并 / 改条款类型 / 标记为非条款」。校正结果**记入修订日志**，可反哺切分器优化。**别让切分变成不可干预的黑盒**。

**④ 必备条款"空槽位"展示（体验差异最大的一条）**

| | 现在的做法 | 建议改成 |
|---|---|---|
| 表达 | 报告写"缺少争议解决条款 → 中风险" | 展示该合同类型**应含的 12 类条款清单**，已识别打勾，缺失的显示为**空槽位卡片** |
| 用户感知 | "你有 5 个风险" | "12 类该有的条款你缺 3 类" |
| 行动 | 需要自己想办法 | 空槽位卡片自带标准示范条款 + "引用到建议" |

配套需要一张 **`合同类型 × 必备条款`矩阵**配置表（采购/销售/服务/劳动各一份），这份表本身就是"规则库"的一部分。

## 十三、综合风险定级的算法（必须可解释）

spec 定义了三级，但**没定义怎么从一堆单项风险算出"这一份合同是高还是中"**。评审一定会问"为什么这份是高危而不是中危"，答不上来整个评级就不可信。

给一个可解释的加权公式：

```
score = 0.40 × 最高单项风险分        # 高=100 / 中=60 / 低=30
      + 0.25 × 高风险项数量分         # min(高风险数, 4) / 4 × 100
      + 0.20 × 风险密度分             # 风险项数 / 条款总数，归一化到 0~100
      + 0.15 × 合同敞口分             # 合同金额与相对方资质的加权

综合等级：score ≥ 70 → 高风险 ；45 ≤ score < 70 → 中风险 ；< 45 → 低风险
```

**一票否决项（任一命中直接判高，不走加权）**：
- 相对方被列入经营异常名录 / 失信被执行
- 我方承担无限责任 / 无上限赔偿
- 管辖地约定违规（约定由对方所在地法院管辖且我方为弱势方）
- 无验收前置条件的全额付款

**界面上把计算过程摊开**：
> 综合风险 **高** ｜ 总分 82 = 最高单项 40（知产归属，高）+ 高风险项数 25（3 项）+ 风险密度 12 + 合同敞口 5

**可解释的评级才敢用于决策**。这一行小字，价值超过再加五条规则。

## 十四、人机协同质量闭环（系统越用越准）

第一轮只做到"采纳/编辑/驳回"三态。补四件事，让它成为一个闭环而不是单向输出：

1. **误报反馈入口**：卡片上一个"这不是风险"按钮 → 写入误报池，记录 `规则 ID + 条款片段 + 反馈人`。大盘显示"本月误报 12 条，集中在 R-LIAB-003"。
2. **建议采纳率**：按规则统计 `采纳数 / 展示数`，形成"**建议质量榜**"。采纳率 < 30% 的规则标黄待优化。
   ⚠️ 注意：**"判定错"（误报）与"建议质量差"（不采纳）是两个独立指标**，不要混成一个。
3. **法务改写归因**：法务编辑 AI 建议时可选原因（措辞不当 / 口径不符 / 过于保守 / 条款不适配），归因结果作为**范本库改进候选**。
4. **一致性校验与分流**：同一份合同用「纯规则模式」和「规则 + LLM 模式」各跑一遍，输出**差异面**。差异大的合同才是真正需要人重点看的——这既是质量监控，也是**人工分流的客观依据**（而不是拍脑袋决定哪份要人审）。

**叙事价值**："系统上线后，高风险规则的建议采纳率从 41% 提升到 76%" —— 这句话证明的是**系统在进化**，不是"我们做完了"。

## 十五、审查本身的可审计性与可复现性

spec 讲的是"原文可追溯"。企业采购还会追问**第二层**：*"三个月后你怎么证明当时那个判断是对的？"*

| 机制 | 做法 |
|---|---|
| **审查快照** | 每次审查落一条 `review_snapshot`：`规则库版本 + prompt 版本 + 模型名/版本 + 温度 + 切分器版本 + 输入哈希` |
| **可复现** | `温度=0` + 结果缓存 `hash(合同文本 + 规则版本 + prompt 版本) → 结果`。同输入同版本 → 同输出，可重复演示、可回归测试 |
| **规则生命周期** | 规则带 `版本 / 生效期 / 状态（draft｜active｜deprecated）`，已废弃规则不参与新审查但历史结论仍可还原 |
| **变更影响面预演** | 改一条规则时，用历史合同跑一遍，输出"**此变更将使 6 份已审合同的结论发生变化：…**" |

最后一条**几乎没人做**。它的意义是防止"改了一条规则，历史报告和系统结论对不上"——这在真实合规场景里是事故，在答辩里是降维打击。

## 十六、成本与性能（企业采购必问）

| 项 | 做法 | 收益 |
|---|---|---|
| **增量审查** | 配合 P1-1 双版本比对，只对**变更的条款块**重跑审查 | 通常省 60~80% 的 LLM 调用 |
| **三段流水线** | 解析 → 规则 → LLM 解耦；规则段先跑，命中确定性高风险直接短路，不进 LLM | 既省钱又快 |
| **条款级并发** | 条款块之间无依赖，可并发送审（注意限流） | 36s → 约 10s |
| **结果缓存** | 标准化后的条款文本命中缓存；示例合同与回归测试大量复用 | 回归测试近乎免费 |
| **成本卡** | 大盘显示"本份 ¥0.12（输入 8.2k / 输出 1.4k tokens）· 累计 ¥3.86" | 主动给数字 |
| **降级** | LLM 不可用时自动切纯规则模式，仍出结果并标注"未执行语义研判" | 不宕机 |

**成本卡是纯加分项**：企业采购一定会算账，**主动给出数字比被问出来好**；而且它天然证明"增量审查"到底省了多少。

## 十七、安全与数据合规（合同是最敏感的数据）

| # | 项 | 做法 |
|---|---|---|
| 1 | **字段级脱敏** | 导出报告 / 回写审批单时，银行账号、身份证号、联系电话按规则掩码（`6222****8888`），可按角色配置 |
| 2 | **敏感信息不出本地** | 语义研判优先走本地模型；若必须走云端，先把主体名称、金额、账号替换为占位符（`<PARTY_A>`、`<AMOUNT_1>`），审查后回填 |
| 3 | **下载水印** | 导出 PDF 带"审查人 + 时间 + 任务号"水印 |
| 4 | **访问留痕** | 谁、何时、查看了哪份合同的哪一页，全部记录 |
| 5 | **数据边界说明** | 报告首页小字注明"本系统数据存储于 XXX，不外传第三方" |

第 2 条在验收答辩里是**强加分项**——它证明你意识到"合同不能随便发给云端大模型"。做到这一点，技术方案的成熟度评价会明显不同。

## 十八、演示工程（现场不出事）

第一轮没提这块，但对"演示型交付"来说最实际。现场翻车一次，前面所有亮点都会被折扣。

| 项 | 做法 |
|---|---|
| **故障注入开关** | mock 审批系统提供 `/mock/fault?mode=timeout｜500｜slow`，**主动演示**阻塞与重试，而不是等它偶发 |
| **一键重置** | `demo_reset` 清空任务/日志/回写记录，恢复到初始 12 份待审状态。演示前跑一次，避免被上次残留数据污染 |
| **降级兜底** | LLM 挂 → 纯规则模式；OCR 挂 → 明确提示"扫描件解析暂不可用"，而不是静默失败 |
| **录屏兜底** | 关键路径（阴阳合同比对、问答）准备 30s 录屏或截图，模型抽风时直接放 |
| **演示数据分层** | 12 份待审固定埋：1 份加密 PDF（阻塞）、1 份空正文 DOCX（阻塞）、2 份场景合同、1 份双版本对、其余正常 |
| **冷启动预热** | 演示前先跑一遍全流程预热（模型加载、向量库连接、缓存填充），避免第一个请求要等 40s |

## 二十、补充后的一句话

第一轮对的是**"别人有什么"**；第二轮对的是**"这类系统本身会漏什么、评审会问什么"**。

**如果只能再加三件事，就加这三个：**
1. **风险分三类来源明示**——把可信度分层，用户才知道该信几分
2. **10 条确定性校验**——零误报，用硬结论给 AI 结论做背书
3. **定级算法可解释**——把"为什么是高危"摊在界面上，这是评委最爱的追问点

这三件事加起来，比再做五个功能模块更能让人相信"这套系统是真懂的"。
