## 一、这是什么

一套面向**企业合同审批场景**的智能审查系统：读取待审批的合同（DOCX / PDF / 扫描件），
自动完成条款结构化切分、法律与商业风险识别、修改建议生成、审批意见回写与报告导出。

**但它不做决定。** 系统只生成审查意见、只写审批评论区，
**不提供通过 / 拒绝 / 转交 / 撤回等任何改变审批结论的动作** —— 最终判断永远属于审批人。

| 项 | 内容 |
| --- | --- |
| 运行环境 | Python 3.11+（实测 3.13.14），**零外部服务依赖**（无需 MySQL / Redis / 消息队列） |
| 技术栈 | FastAPI + SQLite(WAL) + PyYAML + python-docx + PyMuPDF + 可选 RapidOCR |
| 前端 | 原生 HTML / CSS / JS，**零构建、无框架、无 CDN** |
| 规模 | git 追踪 58 个文件 · 后端 30 个 Python · 前端 10 个静态文件 |
| 规则库 | 32 条规则（高 11 / 中 13 / 低 8）· 8 种判定类型 · 14 套标准示范条款 |
| 样例集 | 13 份（DOCX 9 / PDF 3 / 扫描件 1，含 1 份加密阻塞用例） |

## 六、三条值得单独说的设计判断

### 判断一：规则引擎下判定，大模型只做表达

法务场景的结论要**可解释、可复核、可追溯、可审计** —— 大模型自由判断无法同时满足这四条。
因此判定 100% 由 32 条 YAML 规则完成；大模型只解释成因、润色建议、检测跨条款矛盾，
Prompt 中明确禁止新增或修改风险项，输出必须过结构校验，失败即降级为确定性模板生成器。

### 判断二：证据链到字符级

每条风险都必须能落到全文字符串的 `[char_start, char_end)` 区间。
DOCX / PDF / OCR 三种来源映射到同一坐标系，因此前端只需要**一种高亮逻辑**，
而法务可以**逐字核对**系统凭什么这么判。

### 判断三：视角解析防误报

「知识产权归甲方所有」在采购合同里对我方有利，在销售合同里恰恰相反。
规则库用 `{我方}` / `{对方}` 占位书写、运行期按业务类型实例化，
另有三道配套闸门（规则级适用范围、语境排除、共现判定）。

> ### ⚠️ 关于 100% 的诚实声明
>
> 黄金标注与规则库由**同一团队同步编写**。因此 100% 召回是
> **内部回归基线** —— 它的作用是防止「改一条规则、伤三处条款」，
> **不等于**面对全新语料的泛化能力。
>
> 类比：单元测试全绿不代表程序没有 bug，只代表已写下的断言都成立。
> 「我们的规则在自建样例集上召回 100%」可验证；
> 「我们的系统能识别 100% 的合同风险」无法验证 —— **我们说前者**。
>
> 补齐路径（路线图 M2）：① 采集 50–100 份真实脱敏合同；② 由未参与规则编写的法务人员独立标注（盲测）；
> ③ 在盲测集上跑分并公开真实指标（预期低于 100%，这是正常的）；④ 按漏报/误报聚类定向调优。
