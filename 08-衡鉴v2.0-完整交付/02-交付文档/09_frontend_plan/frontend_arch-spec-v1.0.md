# 衡鉴 · 前端架构规范（v1.0）

> **一句话结论**：前端在「零构建」硬约束下采用**两段式**组织 ——
> `common.js` 承担公共能力（请求、格式化、组件、SSE、雷达图），
> 四个页面脚本各自维护**一个模块级状态对象**并显式重渲染；
> 不引入框架、不引入 CDN、不做自动响应式，换来的是「拷到任何机器上双击就能跑」。

| 项 | 值 |
| --- | --- |
| 页面数 | 4 |
| 脚本数 | 5（含公共层） |
| 样式表 | 1（`assets/css/app.css`，CSS 变量驱动） |
| 构建步骤 | **无** |
| 外部依赖 | **无**（无 npm、无 CDN、无图标字体） |
| 浏览器要求 | Chrome / Edge 90+（需支持 SSE 与 CSS Grid） |

## 一、页面清单与路由

| # | 页面 | 路径 | 用途 | 主要接口依赖 |
| --- | --- | --- | --- | --- |
| 1 | 审查大盘 | `/` | 任务总览、筛选、上传、流水线进度 | `stats/overview`、`contracts`、`upload`、`pull`、`events` |
| 2 | 智能审查工作台 | `/pages/workbench.html` | 双栏联动审查、人工审核、回写、报告 | `contracts/{id}`（详情/document/findings）、`adopt`、`annotations`、`hitl`、`human-review`、`writeback*`、`comments`、`report`、`search`、`retry` |
| 3 | 合规规则与模板 | `/pages/rules.html` | 规则树浏览与编辑、示范条款库 | `rules/tree`、`templates`、`PUT rules/{id}` |
| 4 | 评测与观测 | `/pages/eval.html` | 回归跑分、指标明细、系统观测 | `eval/score`、`eval/run`、`stats/overview`、`system/health` |

新增页面只需在 `NAV` 加一项 —— 导航不需要逐页改。

## 二、文件职责边界

| 文件 | 职责 | 禁止 |
| --- | --- | --- |
| `assets/css/app.css` | 设计系统：CSS 变量（色彩/圆角/字体栈）+ 组件样式（卡片/表格/标签/按钮/模态/时间轴/进度条） | 禁止写页面特有的布局代码（页面内联 style 或页面级 `<style>` 处理） |
| `assets/js/common.js` | 公共层：`api()`、格式化（金额/时间/标签）、`toast`、`modal`、顶栏、SSE、雷达图、极简 Markdown | 禁止包含任一面板特有的业务逻辑 |
| `assets/js/dashboard.js` | 大盘页状态与渲染 | 禁止直接 `fetch` |
| `assets/js/workbench.js` | 工作台状态与渲染（高亮联动 / 采纳 / HITL / 回写 / 报告 / 检索） | 同上；禁止在本地硬编码按钮可用性（必须依据后端 `available_actions`） |
| `assets/js/rules.js` | 规则页状态与渲染 | 同上 |
| `assets/js/eval.js` | 评测页状态与渲染 | 同上 |

**唯一请求出口**：所有网络请求必须走 `HJ.api(path, {method, body, form})`。
它统一处理 JSON 序列化、`multipart` 转发、错误提取（把后端 `{detail}` 转成 `Error`）。
绕过它直接 `fetch` 会导致错误提示格式不一致，用户看到的报错会变成 `HTTP 409` 而不是后端给的中文指引。

## 四、核心交互详解

### 4.1 双栏联动（字符区间求交）

这是工作台的核心机制。实现只有两个函数：

```js
function overlap(a1, a2, b1, b2) { return a1 < b2 && b1 < a2; }

function applyHighlights() {
  const ps = [...$('docBody').querySelectorAll('p[data-start]')];
  ps.forEach(p => {
    p.classList.remove('hl-high', 'hl-medium', 'hl-low');
    const s = Number(p.dataset.start), e = Number(p.dataset.end);
    let best = null;
    for (const f of W.findings) {
      if (overlap(s, e, f.char_start, f.char_end)) {
        if (!best || rank(f.level) < rank(best)) best = f.level;   // 取最高等级
      }
    }
    if (best) p.classList.add('hl-' + best);
  });
}
```

**为什么用求交而不是"按段落索引匹配"**：
一条风险可能横跨多个段落（例如付款条款跨页），
而一个段落也可能同时命中多条风险。字符区间求交天然处理了这两种情况，
并且对 DOCX / PDF / OCR 三种来源完全一致 —— 这是统一坐标系带来的红利。

### 4.2 点卡片跳原文

```
focusFinding(f)
  ├─ 找第一个与 f 区间相交的段落
  ├─ scrollIntoView({ behavior:'smooth', block:'center' })
  ├─ 260ms 后加 .pulse（脉冲高亮，播放 2 次后自动消散，不留永久视觉噪音）
  └─ 同步给对应 .fcard 加 .active，并 scrollIntoView 到可视区
```

**260ms 延迟是刻意的**：滚动动画进行中加脉冲会被"吃掉"视觉效果。
动效只在**状态变化**时出现，这是本项目的动效原则。

### 4.3 划选原文反查

绑定在 `document.mouseup`：

1. 取 `window.getSelection()`，为空或长度 < 4 直接返回（避免误触发）；
2. 确认选区落在 `#docBody` 内，并找到最近的 `p[data-start]`；
3. 用 `para.textContent.indexOf(text)` 计算选区在段落内的偏移，换算成全文绝对区间；
4. 过滤出与该区间相交的风险项，弹出「片段研判」；
5. 命中为空时给出明确文案："该片段未命中规则；如需针对性意见，请由法务人工补充批注"
   —— 空态必须解释原因，而不是留白让人以为坏了。

### 4.4 键盘流

| 键 | 行为 | 实现要点 |
| --- | --- | --- |
| `j` / `k` | 下一条 / 上一条风险 | 在 `W.findings` 上移动索引，自动切到「风险项」标签并联动左侧 |
| `Enter` | 采纳当前风险建议 | 触发 `adopt(W.active)` |
| `/` | 聚焦自然语言检索框 | `preventDefault()` 避免浏览器快速查找 |
| `Esc` | 退出输入态 | 在输入元素内按 Esc 时 `blur()` |

**守卫**：当焦点在 `INPUT` / `TEXTAREA` / `SELECT` 内时，除 `Esc` 外全部放行给输入框 ——
否则法务在写批注时按 `j` 会跳到下一条风险，体验会非常糟。

### 4.5 实时进度（SSE）

```js
HJ.streamEvents(contractId, onEvent, { fromSeq })
```

| 要点 | 说明 |
| --- | --- |
| 断线续传 | 事件带自增 `seq`；重连时把已消费的最大 seq 传给 `from_seq` |
| 终止条件 | 收到 `stage` 为 `completed` / `blocked` / `error` 时关闭连接并刷新详情 |
| 心跳 | 服务端每 50 次空轮询发一次 `: keep-alive` 注释行，防止中间层断链 |
| 空闲关闭 | 服务端 `idle_limit` 用尽后发 `event: end`，前端据此结束而不是无限重连 |

## 五、状态管理

### 5.1 约定

| 约定 | 内容 |
| --- | --- |
| 单一状态对象 | 每个页面一个模块级常量对象（大盘 `state`、工作台 `W`、规则页 `R`） |
| 显式重渲染 | 状态变更后显式调用渲染函数（`renderHead()` / `renderDoc()` / `renderRight()`），不做自动响应式 |
| 渲染函数纯读 | 渲染函数只读状态、只产出 DOM 字符串，不修改状态 |
| 事件处理只改状态 | 事件处理函数改状态后调用渲染函数 |

**为什么不用响应式**：页面复杂度（4 页、最大单页约 700 行 JS）下，
显式重渲染的行为**完全可预测**；引入响应式反而会带来"为什么这里没更新"的调试成本，
而且与"零构建"约束冲突。

### 5.2 刷新策略

| 页面 | 策略 |
| --- | --- |
| 大盘 | 8 秒定时刷新列表与统计；**若正在跟踪 SSE 则跳过定时刷新**（避免与事件流抢渲染） |
| 工作台 | 事件驱动：SSE 到终态时整页重载一次（`loadAll`），不做局部 patch |
| 规则页 | 操作后全量重载（规则数量小，重载成本可忽略） |
| 评测页 | 手动触发刷新 |

## 六、状态与空态设计

| 状态 | 呈现 | 文案原则 |
| --- | --- | --- |
| 加载中 | `.spin` 旋转指示 + 文字说明 | 说明"正在做什么"，不是"加载中" |
| 空列表 | `.empty` 居中提示 | 说明"为什么空"与"下一步做什么" |
| 阻塞态 | `.banner` 红色横幅 + 重试按钮 | 必须给出**具体原因**与**处理建议**，六种阻塞码各不同 |
| 无审查结果 | `.empty` | 区分"尚未审查"与"审查完成但无风险" |
| 回写预览态 | 标签显示「预览模式（DRY_RUN）」 | 让用户清楚"这次没有真正写出去" |
| 错误 | `HJ.toast(msg, 'err')` 右下角 | 直接展示后端 `detail`（它是中文的操作指引，不是技术堆栈） |

## 七、设计系统

### 7.1 色彩变量（取自 `app.css :root`）

| 变量 | 值 | 用途 |
| --- | --- | --- |
| `--bg` | `#0B0E14` | 页面底色 |
| `--bg-1` | `#11161F` | 卡片 / 顶栏 |
| `--bg-2` | `#161C27` | 卡片内嵌区 / 风险卡 |
| `--bg-3` | `#1D2533` | 悬停态 / 按钮底 |
| `--line` / `--line-2` | `#232C3B` / `#2E394B` | 分隔线与边框（两级） |
| `--text` / `--text-2` / `--text-3` | `#E6EAF2` / `#A7B0C0` / `#6E7A8D` | 三级文字层次 |
| `--brand` | `#4C8DFF` | 主色（链接、主按钮、选中态） |
| `--high` / `--medium` / `--low` | `#FF5D5D` / `#FFA93B` / `#7C8798` | 风险三级（红 / 橙 / 灰） |
| `--ok` | `#35CE8D` | 成功态、通过态 |
| `--radius` / `--radius-sm` | `10px` / `6px` | 圆角两级 |

**为什么用深色**：审查工作台是长时间盯屏的**工作界面**而非展示页。
深色底 + 高对比文字能降低长时间阅读几十页合同正文的视觉疲劳，
同时让红色风险高亮在页面上"跳出来"。

### 7.2 字号与间距

| 层级 | 字号 | 用途 |
| --- | --- | --- |
| 页面标题 | 17–19px | 页面主标题 |
| 卡片标题 | 13–15px | 区块标题 |
| 正文 | 13–14.2px | 界面文字与文档正文（文档区行高 1.95，便于逐行核对） |
| 辅助 | 11–12.5px | 元信息、标签、脚注 |
| 等宽 | `--mono` | 编号、坐标、耗时、幂等键等需要逐字符比对的字段 |

**等宽字体是刻意的**：规则编号（`HJ-H-002`）、字符区间（`[627,687)`）、
幂等键这类信息会被用户**逐字符核对**，用等宽能显著降低看错一位的概率。

### 7.3 动效原则

| 原则 | 落地 |
| --- | --- |
| 只用于表达状态变化 | 高亮脉冲（定位成功）、卡片入场、流水线点亮、旋转指示 |
| 时长短 | 0.13–0.35s；脉冲 1.1s × 2 次后消散 |
| 不留永久噪音 | 脉冲动画结束即回到常态，不做常驻闪烁 |
| 尊重克制 | 无背景动画、无滚动视差、无装饰性过渡 |

## 八、响应式与降级

| 断点 | 行为 |
| --- | --- |
| ≥ 1180px | 工作台双栏（文档区 + 440px 侧栏）；大盘两栏（列表 + 侧栏） |
| 900–1180px | 大盘两栏塌成单栏；工作台工具栏换行 |
| < 900px | 全部单栏堆叠；文档区宽度自适应；筛选控件换行 |

**流量轴**：工作台的流程节点在窄屏下从横向改为纵向换行（`.flow { flex-wrap: wrap }`），
不做横向滚动 —— 横向滚动在演示投屏时极易出错。

**降级**：
- 无 JavaScript：显示静态说明（当前未做 SSR，属【未开发】）；
- 无 SSE 支持：`common.js` 的 `streamEvents` 会静默失败，页面依赖定时刷新兜底（大盘已具备）。

## 九、已知局限

| # | 局限 | 影响 |
| --- | --- | --- |
| 1 | 无前端构建与模块打包 | 单页 JS 增长后需手工拆分，无 tree-shaking |
| 2 | 无自动化前端测试 | 交互正确性依赖接口冒烟 + 人工验证（【未开发】） |
