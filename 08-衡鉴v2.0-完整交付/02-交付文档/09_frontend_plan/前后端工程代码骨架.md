# 衡鉴 · 前后端工程代码骨架

> **一句话结论**：后端严格三层（`api → services → db/config`，依赖只向下），
> 前端在"零构建"约束下用"公共层 + 页面脚本"两段式组织；
> 本文给出与真实仓库一致的目录树、关键函数签名，以及"新增接口 / 新增规则 / 新增页面"三个可照做的步骤。

## 二、后端分层骨架

### 2.1 依赖方向（**只允许向下**）

```
        api/            路由层：解析请求、调用服务、组装响应、抛 HTTPException
         │              禁止：写 SQL、写业务规则、import 其他 service 的内部实现
         ▼
      services/         业务层：全部业务逻辑在这里；可互相调用（同层）
         │              禁止：import api/（反向依赖）、拼 HTTP 响应
         ▼
     db.py / config.py  基础设施层：连接、事务、DDL、配置常量
                        禁止：import 任何业务模块
```

**为什么这条规则值得写进文档**：
反向依赖一旦出现（service 里 `from ..api import contracts`），
就会出现"改一个接口签名导致服务层报错"的连锁反应，
而且 import 循环在 Python 里往往是运行时才炸，很难查。

## 三、前端骨架（零构建约束下的组织方式）

### 3.1 约束与应对

| 约束 | 应对 |
| --- | --- |
| 不用 npm / 不用构建工具 | 原生 ES 模块风格但不使用 `import`（避免 file:// 限制），用 IIFE + 全局命名空间 `HJ` |
| 不用 CDN（断网可演示） | 所有样式与脚本本地文件；图标用 Unicode 字符而非图标字体 |
| 不用框架 | 页面脚本直接操作 DOM；"组件"用模板字符串函数表达（如 `HJ.radar()` / `HJ.riskTag()`） |

### 3.2 两段式模块划分

| 层 | 文件 | 职责 | 禁止 |
| --- | --- | --- | --- |
| **公共层** | `common.js` | `api()` 请求封装、格式化（金额/时间/标签）、`toast`、`modal`、顶栏注入、`streamEvents`(SSE)、`radar`(SVG 雷达图)、`md()` 极简 Markdown 渲染 | 禁止写任何单个页面特有的业务逻辑 |
| **页面层** | `dashboard.js` / `workbench.js` / `rules.js` / `eval.js` | 单个页面的状态、渲染、事件绑定 | 禁止绕过 `HJ.api()` 直接 `fetch`；禁止硬编码接口地址 |

### 3.3 无框架状态组织

每个页面脚本维护**一个模块级状态对象**，渲染函数只读它、事件处理函数只改它：

```js
// workbench.js
const W = {
  id: null, task: null, doc: null, findings: [], review: null,
  writeback: {}, active: null, tab: 'findings', es: null, clauseRanges: [],
};
```

**约定**：状态变更后显式调用对应渲染函数（`renderHead()` / `renderDoc()` / `renderRight()`），
不做自动响应式。页面规模在这个量级下，显式重渲染比引入响应式系统更可预测、更好调试。

## 四、三个标准操作步骤（可照做）

### 4.1 新增一个接口

1. **定义契约** → 在 `app/schemas.py` 加请求模型（有请求体时）；
2. **实现业务** → 在 `app/services/` 对应模块加函数，**不要在路由里写业务**；
3. **挂路由** → 在 `app/api/contracts.py` 或 `rules.py` 加 `@router.xxx`，只做"取参 → 调服务 → 返回"；
4. **补冒烟** → 在 `tools/smoke_api.py` 加 `check(...)` 断言（含正常与异常分支）；
5. **补文档** → 在 `docs/08_api_spec/api_spec-v1.0.md` 增补接口章节；
6. **跑验证** → `python -m pytest -q && python tools/smoke_api.py`。

### 4.2 新增一条规则

1. 在 `app/rules/rules_v1.yaml` 的 `rules` 下追加，**必填** `id / title / level / type`；
2. 判定参数写在 `params`，判定类型必须是 8 种之一（CI 会校验白名单）；
3. 若引用示范条款，`advice_ref` 指向 `clause_templates.yaml` 中**已存在**的 `id`（CI 校验引用完整性）；
4. 若规则只适用特定业务类型，加 `biz_types: ["采购", "服务"]`；
5. 若涉及视角，关键词里用 `{我方}` / `{对方}` 占位；
6. **升级文件头的 `version`**；
7. 在 `tests/test_rule_engine.py` 补一条针对性用例（正例 + 反例）；
8. 在 `tools/gen_samples.py` 相应样例中埋点或加入干净基线，并更新 `expect_high`；
9. 重跑：`python tools/gen_samples.py && python -m app.eval.run_eval && python -m pytest -q`。

> 第 8 步容易漏。规则和样例是**成对演化**的：改了规则不更新标注，
> 评测就会开始报"误报"或"漏报"，然后你会去怀疑规则引擎 —— 其实只是标注过期了。

### 4.3 新增一个页面

1. 在 `frontend/pages/` 建 `xxx.html`，引 `common.js` + `xxx.js`；
2. 在页面里放一个 `<header id="topbar"></header>`，脚本里调 `HJ.mountTopbar('<key>')`；
3. 在 `common.js` 的 `NAV` 数组加一项，导航自动出现（含当前页高亮）；
4. 新建 `frontend/assets/js/xxx.js`，用 IIFE + 模块级状态对象；
5. 在 `tools/smoke_api.py` 的静态前端检查列表里加一条，确保页面可访问；
6. 在 `docs/05_prototype/前端交互设计规范.md` 补页面清单与层级。
