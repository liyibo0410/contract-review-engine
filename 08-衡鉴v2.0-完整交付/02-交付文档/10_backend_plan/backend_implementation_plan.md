| 项 | 内容 |
| --- | --- |
| **目标** | 生成 13 份样例（含 2 份埋雷合同、1 份加密件、1 份扫描件）与黄金标注 |
| **完成标志** | `samples/` 齐全，双击可打开；`golden_cases.json` 与样例同源 |
| **实际状态** | ✅ 完成 |
| **证据** | `python tools/gen_samples.py` → DOCX 9 / PDF 3 / 扫描件 1，共 13 份；黄金标注含 `expect_high` / `expect_medium` / `expect_blocked` |
| **产出** | `tools/gen_samples.py`、`samples/*`、`app/eval/golden_cases.json` |

**为什么用脚本生成而不是手工准备文件**：

| 理由 | 说明 |
| --- | --- |
| 可复现 | 任何人 clone 后跑一条命令得到完全一致的样例集 |
| 可标注 | 生成时同步产出期望清单，**评测集与样例集永远同源**，不会"文件换了、标注没换" |
| 可控 | 每份合同埋哪些雷、哪些是干净的，都在一处可查可审 |

**技术实现**：DOCX 用 python-docx（含显式分页符以产生真实页码）；
PDF 用 PyMuPDF 内置 `china-s` 中文字体；扫描件用 PIL 渲染 + 高斯模糊 + 轻微旋转 + 噪点模拟真实复印件；
加密件用 PyMuPDF AES-256 加密。

## S3 · 解析引擎

| 项 | 内容 |
| --- | --- |
| **目标** | DOCX / PDF / OCR 三引擎 → 段落树 + `{page, para_index, char_start, char_end}` |
| **完成标志** | 13 份全部解析成功，坐标可回显原文 |
| **实际状态** | ✅ 完成（解析成功率 **100%**） |
| **证据** | `pytest tests/test_parsers.py`（13 个用例）；评测报告解析成功率 100% |
| **产出** | `parser_docx.py`、`parser_pdf.py`、`parser_ocr.py`、`coordinator.py` |

**关键设计**：

| 设计 | 说明 |
| --- | --- |
| 统一坐标系 | 全文 `full_text` 是唯一真理坐标；任何风险必须落到 `[char_start, char_end)` |
| DOCX 页码来源 | 识别 `w:lastRenderedPageBreak` 与显式分页符；**无分页信息时如实退化为 page=1**，不伪造 |
| 图片型 PDF | 页文本为空时自动回退渲染成位图交 OCR，与文本型共用坐标系 |
| OCR 缺失不崩 | 抛 `OcrUnavailable` 可读异常，协调器转为 `blocked` 并区分"引擎缺失"与"图片模糊" |
| 加密 PDF | `needs_pass` 且无密码 → `PdfEncrypted` → `DOC_ENCRYPTED` |

**踩坑记录（真实）**：条款分类关键词表里最初放了角色词（甲方 / 乙方 / 供方 / 需方）。
角色词在合同里无处不在，导致"知识产权段落"被判成"签约主体段落"，整篇条款类型错位、
基于 `clause_type` 的规则全部失效。
**修复**：① 角色词从打分表移除，主体类只认主体属性词；② 类型切换改为"严格优于当前上下文才切换"（平局保持归属）。

## S4 · 规则引擎 + 评测

| 项 | 内容 |
| --- | --- |
| **目标** | 32 条 YAML 规则（高 11 / 中 13 / 低 8）+ 回归评测脚本 |
| **完成标志** | `run_eval.py` 输出高风险召回 100% 与四项指标 |
| **实际状态** | ✅ 完成（召回 100% / 误报 0 / 判定 PASS） |
| **证据** | `pytest tests/test_rule_engine.py`（11 个用例覆盖 8 种判定与视角解析）；`python -m app.eval.run_eval` |
| **产出** | `rule_engine.py`、`rules_v1.yaml`、`clause_templates.yaml`、`app/eval/run_eval.py` |

**实现要点**：

| 要点 | 说明 |
| --- | --- |
| 8 种判定类型 | keyword / regex / numeric / imbalance / imbalance_regex / missing_clause / required_combo / absent |
| 视角解析 | 规则用 `{我方}` / `{对方}` 占位，运行期按业务类型实例化 |
| 规则级适用范围 | `biz_types` 控制（如"付款须挂钩验收"不适用于劳动合同） |
| 语境排除 | `exclude_keywords`（如"累计不超过 20%"是上限保护，不是违约金风险） |
| 共现判定 | `required_combo` 只在同一句同时出现付款与验收语境时才认定"已挂钩" |
| 去重与排序 | 同规则同区间去重；按等级 → 页码 → 字符位置排序 |

**开发期的三次迭代（真实过程）**：
① 首轮跑分召回率仅 **45%** —— 定位到条款分类错位（见 S3 踩坑）；
② 修复分类后仍有误报：`HJ-H-002` 在标准合同与劳动合同上误报 —— 引入 `biz_types` 与共现判定；
③ 违约金规则把"累计不超过合同总价的 20%"（上限保护）误判为比例风险 —— 引入 `exclude_keywords` 与多模式匹配。
最终达到召回 100% / 误报 0。

## S5 · LLM 语义层

| 项 | 内容 |
| --- | --- |
| **目标** | 证据约束 Prompt + JSON 校验 + 降级模板生成器 |
| **完成标志** | 断网测试：降级路径自动接管，输出仍完整 |
| **实际状态** | ✅ 完成 |
| **证据** | `pytest tests/test_pipeline.py::test_llm_degradation_produces_complete_output` 通过；本机未配 Key 状态下端到端演示正常产出摘要与建议 |
| **产出** | `llm.py`、`writer.py`（模板降级器） |

**三条边界（代码级约束）**：

1. **不下判定** —— 只接收"已命中的证据"；Prompt 中明确禁止新增 / 删除 / 合并风险项、禁止修改等级；
2. **输出必须过校验** —— 只接受符合结构的 JSON；解析失败 / 超时 / 网络异常一律降级；
3. **可审计** —— 每次调用把耗时、是否降级、失败原因写进 `audit_logs`。

**为什么用标准库 `urllib` 而不是 `openai` SDK**：
少一个依赖就少一个演示现场出问题的理由；且 OpenAI 兼容协议本身足够简单。
另外显式绕过系统代理（`ProxyHandler({})`），避免本机代理把请求拦成 502 这类难定位的问题。

**踩坑记录（真实）**：
- `run_review()` 内写了 `import json as _json`，**遮蔽了模块级 `_json()` 函数**，
  导致流水线抛 `'module' object is not callable`，所有任务变成 `blocked`。
  → 局部 import 改名去掉，模块级统一 `import json`。
- 任务编号只精确到秒，同秒创建两个任务导致幂等键撞唯一索引。
  → 编号末尾追加 4 位随机码，并补单元测试锁定。
- `api/contracts.py` 漏导入 `parser_docx`，`GET /document` 返回 500。
  → 补全导入；此类"漏导入"说明**冒烟必须覆盖每一个接口**，不能只挑常用接口。
