# 合同审核场景调研

**一句话结论**：合同/法务类文档审核是企业里最容易被 Agent 技术降耗、又最不能让 Agent 越权的场景——衡鉴用"确定性规则 + 大模型语义增强"双引擎把风险定位到字符级，并用四个人工中断点（HITL）把最终审批权牢牢留在人手里。

> 本文档所有数字、规则 ID、接口名均来自 `docs/00_setup/项目事实基线.md`，未引用任何基线之外的量化数据。

---

## 1. 场景目标

**一句话**：在合同进入审批流程之前，自动完成一次"数字法务"级别的预审，输出可定位、可追溯、可回写的审查意见，但不替任何人做"通过 / 拒绝"的决定。

展开说明，这个场景要同时解决三件事：

| 目标 | 含义 | 为什么必须做 |
| --- | --- | --- |
| 风险可定位 | 每一条风险都能落到原文 `[char_start, char_end)` 区间 | 法务只有看到"原话在哪、为什么判"，才会采信结论 |
| 依据可追溯 | 每条命中都带 `reason` / `legal_basis` / 证据链 | 审查意见要经得起被审计、被复议、被诉讼引用 |
| 意见可回写 | 结论只写进审批系统的"评论区"，不写审批结论 | 不改变审批权责，系统只提供意见不替人决策（基线第九章红线） |

---

## 2. 审核对象：合同及其条款分类

审核对象是一份份企业合同（DOCX / PDF / 扫描件三种来源），系统先把全文切成**条款结构树** `clauses`，再按 11 类 `clause_type` 本体归类。分类是后续规则判定的作用域基础——一条规则只在它声明的 `clause_type` 内生效，避免跨条款误伤。

| clause_type | 中文 | 典型风险面 |
| --- | --- | --- |
| `subject` | 签约主体与资质 | 相对方主体异常、未要求资质证明 |
| `subject_matter` | 标的物 | 标的描述不清、范围模糊 |
| `payment` | 价款与支付 | 付款无验收前置、预付款过高、违约金过高 |
| `delivery` | 交付与验收 | 缺失验收标准、交付期限模糊 |
| `liability` | 违约责任 | 严重不对等、我方无限责任、违约金超 30% |
| `confidentiality` | 保密义务 | 无期限、单向设置、竞业限制无补偿 |
| `ip` | 知识产权 | 归属相对方、缺失条款 |
| `data_security` | 数据安全 | 无个人信息/数据保护条款 |
| `dispute` | 争议解决与管辖 | 约定在对方所在地、缺失条款 |
| `validity` | 合同效力 | 有效期不明、份数附件效力缺失 |
| `force_majeure` | 不可抗力 | 缺失条款、无通知时效 |
| `other` | 其他 | 通知送达缺失等兜底 |

**为什么是 11 类而不是更少**：基线在条款切分上有明确踩坑记录——角色词（甲方/乙方）一旦计入打分，会把"知识产权段"错判成"签约主体段"，连带整篇风险命中失效。因此条款词表刻意不含角色词，分类树只靠**标题正则识别 → 标题语义向下传播 → 正文需 2 个关键词自证才允许切换类型**，且切换要求**严格优于当前上下文**（平局保持归属）。

## 3. 为什么必须有人机交互流程（interrupt / HITL）

### 3.1 法律审查的"不可自动化"本质

合同审查不是分类问题，是**责任判断问题**。系统能稳定做的是"按规则找风险"，但"这份合同能不能签"涉及商业权衡、谈判空间、过往合作、战略取舍——这些只能由人定。因此流程必须设计成"机器跑完、人来做决定"，而不是"机器跑完、自动放行"。

### 3.2 与 LangGraph `interrupt` 的对应关系

基线任务状态机 `pending → parsing → reviewing → completed`，并在 `parsing` / `reviewing` / `applying` 设中断点。这与 LangGraph 的 `interrupt` 语义一致：**中断点不是报错，而是流程主动停下来等人做决定**，且每个中断点都要给出可执行的下一步动作。

本项目的四个 HITL 动作：

| 动作 | 语义 | 系统行为 | 对应中断点 |
| --- | --- | --- | --- |
| `approve` | 同意系统审查结论 | 记录流水，解锁回写 | `reviewing` |
| `edit` | 改风险等级 / 改写建议后确认 | 更新 `findings`，重算综合风险与结论，`reviews.generated_by` 标记 `human_edited` | `reviewing` |
| `reject` | 驳回审查结果 | 清空本次 findings/reviews，任务回 `pending` 并自动重跑 | `reviewing`（被驳回） |
| `resume` | 从阻塞中断点恢复 | 等价于 retry，但保留中断上下文 | `parsing`（blocked） |

`applying` 阶段还保留 `reject`（撤回确认）作为人工反悔入口。

### 3.3 为什么 HITL 落"动作流水"而不是"状态字段"

基线设计要点：`hitl_actions` 记录的是**业务决策**（谁、什么时候、同意/修改/驳回了什么），`audit_logs` 记录的是**系统执行**（哪个 step、用了什么 tool、输入输出摘要）。前者天然可追溯，"谁改了什么"就是业务数据本身，不需要额外维护状态迁移日志。这样审计信息即业务数据，降低了状态不一致的风险。

**价值小结**：HITL 让系统在不越权的前提下，把"机器快速初筛 + 人做关键决策"的分工固化成可重放的流程，既提速又不失控。

## 4. 三类用户的真实工作流与痛度量级

以下痛能量级为定性估计（高/中/低 + 说明），**非实测问卷数据**，用于场景建模，不进入量化考核。

### 4.1 法务审查人

| 环节 | 当前做法（无系统） | 痛点 | 量级 |
| --- | --- | --- | --- |
| 收合同 | 业务把合同甩进审批流 | 到手已是"待签"状态，发现太晚 | 中 |
| 通读 | 逐条读 10+ 页文本 | 一份合同平均 30–60 分钟，重复劳动 | 高 |
| 标风险 | 红字批注 / 写审查意见 | 定位靠"大概在第几页"，复核困难 | 高 |
| 提意见 | 复制示范条款改一改 | 示范条款散落，每次重写 | 中 |
| 归档 | 邮件/IM 来回 | 意见与原文脱钩，事后难溯源 | 中 |

**系统价值**：统一坐标系把定位从"第几页"降到字符区间；32 条规则覆盖 11 类条款，把通读时间压缩到"看风险卡片"；回写只落评论区，不碰审批结论。

### 4.2 业务经办人

| 环节 | 当前做法 | 痛点 | 量级 |
| --- | --- | --- | --- |
| 起草/拿合同 | 对方模板或历史模板 | 不知道哪条坑是自己的 | 高 |
| 等法务 | 被动等反馈 | 法务忙时排队数天 | 高 |
| 改合同 | 来回沟通 | 改了哪、为什么改，信息断层 | 中 |
| 过审批 | 走 OA / 审批系统 | 系统只收结论，不收"为什么" | 中 |

**系统价值**：预审在审批前完成，经办人能提前看到"埋雷点"并自助整改；`/{id}/search` 支持自然语言检索条款，经办人能自己查"违约金那条在哪"。

### 4.3 系统管理员

| 环节 | 当前做法 | 痛点 | 量级 |
| --- | --- | --- | --- |
| 部署 | 手动装环境 | Python 依赖、OCR 引擎缺装即崩 | 中 |
| 规则维护 | Excel/口头传 | 规则无版本、无校验、无法回归 | 高 |
| 监控 | 出问题才看日志 | 无统一健康视图 | 中 |
| 合规留痕 | 分散在邮件 | 审计要翻多个系统 | 中 |

**系统价值**：`PUT /api/rules/{rule_id}` 改规则落盘 YAML 并升版本；CI 四道门禁（静态检查 / 单测 / 回归跑分 / 镜像构建）保证"改一条规则不伤三处条款"；`/api/system/health` + `audit_logs` 提供统一可观测性。

---

## 5. 对后续阶段的输入要求（摘要，详见 business_summary.md）

1. 规则体系必须覆盖全部 11 类 `clause_type`，新规则入库存前过 CI 门禁；
2. 双引擎分工不变：规则引擎做**唯一判定来源**，LLM 只做解释/建议/跨条款矛盾检测；
3. HITL 四动作是硬约束，任何重构不得削弱"人做最终决定"的链路；
4. 统一坐标系是所有前端高亮与回写的基础，禁止各格式各自为政。
