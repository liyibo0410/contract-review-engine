# 衡鉴 · 集成联调计划

> **一句话结论**：联调按**业务链路顺序**推进（上传 → 进度 → 详情 → 风险 → 人工审核 → 回写 → 报告），
> 每步有独立验收标准；截至本版本，**单元测试 39/39、接口冒烟 64/64、端到端演示 8 步全部通过**，
> 联调过程中暴露的 5 个真实缺陷已全部修复并记录在第六章。

| 项 | 值 |
| --- | --- |
| 联调范围 | 后端 33 个路径 ↔ 前端 4 个页面 |
| 联调方式 | ① ASGI 直连冒烟（不需要起服务器）② 端到端业务脚本 ③ 真实页面人工验证 |
| 当前状态 | ✅ 全部通过 |

## 一、联调前置条件

| 项 | 要求 |
| --- | --- |
| 运行时 | Python ≥ 3.11（实测 3.13.14） |
| 依赖管理 | uv 0.12+ |
| 依赖安装 | `uv venv --python 3.11 .venv && uv pip install --python .venv/Scripts/python.exe -e .` |
| OCR（可选） | `uv pip install --python .venv/Scripts/python.exe rapidocr-onnxruntime` |
| 样例数据 | `cd backend && python tools/gen_samples.py`（生成 13 份样例 + 黄金标注） |
| 数据库 | 自动创建于 `backend/data/hengjian.db`，无需手工建库 |
| 大模型 | **可不配置**。未配置时语义层走确定性模板生成器，联调不受阻 |
| 启动 | `cd backend && ..\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8130` |

> **为什么要强调"可不配置大模型"**：如果联调依赖外部模型可用性，
> 那么网络波动、Key 到期、限流都会伪装成"功能坏了"。
> 把模型变成可降级的增强项，联调才能稳定复现问题。

## 二、分步联调清单

### 步骤 1 · 上传文档

| 项 | 内容 |
| --- | --- |
| 接口 | `POST /api/contracts/upload`（multipart） |
| 请求 | `file=@01_软件采购合同_埋雷版.docx`，`biz_type=采购`，`auto_run=false` |
| 期望响应 | `200`，返回 `contract_id` / `code` / `reused=false` / `sha256`（64 位十六进制） |
| 验收标准 | ① `code` 形如 `HJ-YYYYMMDD-HHMMSS-xxxx`；② `sha256` 与本地 `certutil -hashfile <file> SHA256` 一致；③ `reused=false` |
| 失败排查 | `400` → 检查扩展名是否在白名单；`413` → 文件是否超过 30MB |

### 步骤 2 · 创建任务与幂等

| 项 | 内容 |
| --- | --- |
| 接口 | 再次调用 `POST /api/contracts/upload`，传同一个文件 |
| 期望响应 | `reused=true`，`contract_id` 与步骤 1 相同，`auto_run=false` |
| 验收标准 | 数据库中 `documents` 表**没有新增**该 sha256 的记录 |
| 失败排查 | 若 `reused=false` → 检查文件是否被重新保存过（内容变了 sha256 就变了） |

### 步骤 3 · 进度跟踪（SSE）

| 项 | 内容 |
| --- | --- |
| 接口 | `GET /api/contracts/{id}/events?from_seq=0&idle_limit=1` |
| 期望响应 | `Content-Type: text/event-stream`，随后推送 `data: {"seq","stage","message","progress",...}` |
| 验收标准 | ① 响应头含 `text/event-stream`；② 事件 `stage` 覆盖 `parsing` → `reviewing` → `completed`；③ `progress` 单调不减至 100 |
| 失败排查 | 浏览器里进度条不动 → 检查 Nginx 是否配了 `proxy_buffering off`（缓冲会积压事件） |

### 步骤 4 · 跑完整流水线

| 项 | 内容 |
| --- | --- |
| 接口 | `POST /api/contracts/{id}/pipeline?wait=true` |
| 期望响应 | `{"status":"completed", ...}`，含 `findings` / `stats` / `summary` / `profile` / `risk_level` |
| 验收标准 | ① `status=completed`；② `stats.high >= 5`（埋雷合同）；③ 每条 finding 都有 `char_start`/`char_end`/`legal_basis`/`advice` |
| 失败排查 | `status=blocked` → 读 `contracts.block_code` 与 `block_reason`（六种阻塞代码见 API 规范）；`status=blocked` 且 `block_code=PIPELINE_ERROR` → 查 `audit_logs.detail` |

### 步骤 5 · 审查结果查询

| 项 | 内容 |
| --- | --- |
| 接口 | `GET /api/contracts/{id}` / `GET /api/contracts/{id}/document` / `GET /api/contracts/{id}/findings` |
| 期望响应 | 详情含 `task`/`document`/`meta`/`profile`/`review`/`writeback`/`clauses`；文档含 `paragraphs[]`；风险含 `items[]` |
| 验收标准 | ① `clauses` 非空且区间连续；② 每条 finding 的坐标能在 `paragraphs` 中**取回非空原文**（见下） |
| 失败排查 | `500 文档重渲染失败` → 检查 `backend/data/uploads/` 下附件是否还在 |

**坐标回显校验方法**（这是整套联调里最关键的一条断言）：

```python
def slice_by_coords(paragraphs, start, end):
    out = []
    for p in paragraphs:
        if p["char_start"] < end and start < p["char_end"]:
            out.append(p["text"][max(0, start - p["char_start"]):
                                 min(len(p["text"]), end - p["char_start"])])
    return "".join(out)
# 断言：slice_by_coords(...) 的结果应非空，且与 findings.evidence_text 有实质重叠
```

### 步骤 6 · 采纳建议

| 项 | 内容 |
| --- | --- |
| 接口 | `POST /api/contracts/{id}/findings/{fid}/adopt`，body `{"adopted":true,"adopted_text":"..."}` |
| 期望响应 | `{"ok":true,"finding_id":fid,"adopted":true,"adopted_text":"..."}` |
| 验收标准 | 重新拉 findings，该条 `adopted=true` 且 `adopted_text` 与提交值一致 |
| 失败排查 | `404` → finding_id 不属于该 contract_id |

### 步骤 7 · 人工审核（HITL）

| 项 | 内容 |
| --- | --- |
| 接口 | `GET /api/contracts/{id}/hitl` → `POST /api/contracts/{id}/human-review` |
| 期望响应 | 状态查询返回 `interrupt_at` / `available_actions`；提交返回 `{"ok":true,"applied":[...]}` |
| 验收标准 | ① 首次查询 `available_actions = ["approve","edit","reject"]`；② `action=edit` 后该 finding 的等级/建议已变更且 `advice_source="manual"`；③ 综合风险等级与 `conclusion` 已重算；④ 审核流水 `history` 递增 |
| 失败排查 | `409` → 检查任务是否 `completed`；`edit` 报 `400` → 检查是否传了 `edits` |

### 步骤 8 · 回写审批

| 项 | 内容 |
| --- | --- |
| 接口 | `GET .../writeback/preview` → `POST .../writeback` |
| 期望响应 | 预览返回 `preview`（Markdown 正文）与 `idem_key`；回写返回 `{"status":"success","platform_comment_id":"CMT-xxxxxx"}` |
| 验收标准 | ① `dry_run=true` 时 `GET .../comments` 返回 **0 条**；② `dry_run=false` 后返回 **1 条**；③ 再次回写返回 `skipped=true`，评论区仍 **1 条** |
| 失败排查 | `409` → 任务未完成，或审查结果被人工驳回（需重跑流水线） |

### 步骤 9 · 报告导出

| 项 | 内容 |
| --- | --- |
| 接口 | `GET /api/contracts/{id}/report`（Markdown）与 `...report?download=true`（PDF） |
| 期望响应 | Markdown 为 JSON；PDF 为二进制流，前 4 字节 `%PDF` |
| 验收标准 | ① Markdown 含"一、合同基本信息"至"五、回写与留痕"五章；② PDF 可打开且中文不乱码 |
| 失败排查 | PDF 乱码 → 确认 PyMuPDF 版本支持内置 `china-s` 字体；导出 Markdown 兜底 |

### 步骤 10 · 异常与降级

| 用例 | 构造方式 | 期望表现 |
| --- | --- | --- |
| 加密文档阻塞 | 上传 `13_软件采购合同_加密件.pdf` 并跑流水线 | `status=blocked`，`block_code=DOC_ENCRYPTED`，原因文案可读 |
| 阻塞重试 | `POST .../retry` | 文件未换仍 `blocked`，且 `clauses` 表**无残留数据** |
| OCR 未安装 | 卸载 `rapidocr-onnxruntime` 后上传扫描件 | `block_code=OCR_ENGINE_UNAVAILABLE`，原因明确写"引擎缺失"而非"图片模糊" |
| LLM 不可用 | 不配置 `HJ_LLM_API_KEY` | 审查照常完成，`reviews.generated_by="template"`，摘要/建议/结论完整 |
| 回写失败重试 | 在 `_submit_to_platform` 中注入异常 | 状态落 `failed` 并保留 `error`；恢复后 `POST .../writeback/retry` 成功 |
| 幂等跳过 | 相同文件与规则版本连续回写两次 | 第二次返回 `skipped=true`，`audit_logs` 出现 `writeback.skip` 警告级日志 |

**接口冒烟为什么用 ASGI 直连而不是起真实服务器**：
在受限开发环境里，从 shell 启动的进程会随命令结束被回收，
"起了服务再测"极易测到"进程已死"而误判成接口故障。
ASGI 直连走的是同一套路由与中间件，结论等价，且不受进程生命周期影响。

冒烟报告落盘于 `docs/13_delivery/接口冒烟测试报告.txt`（64 项逐条结果）。

**端到端实测关键输出**：

```
[2/8] 文档解析   python-docx · 4 页 / 1245 字 / 10 个条款节点
[3/8] 双引擎审查  命中 11 项（高 6 / 中 2 / 低 3），规则判定 1 ms，结论「建议拒绝」
[5/8] 回写       DRY_RUN 预览 1732 字 → 真实写入 CMT-000001 → 重复触发幂等跳过 → 评论区 1 条
[6/8] 报告       Markdown 3360 字 + PDF
[8/8] 异常       加密件 DOC_ENCRYPTED → 重试仍 blocked 且不产生脏数据
```

## 六、联调问题清单（真实发生，全部已修复）

| # | 现象 | 根因 | 修复 |
| --- | --- | --- | --- |
| 1 | 01 埋雷合同的高风险只命中 2 条，条款类型大面积错位 | 条款分类关键词表里放了**角色词**（甲方/乙方/供方/需方）。角色词在合同里无处不在，"知识产权段"被打成"签约主体段"，连带基于 `clause_type` 的规则全部失效 | ① 从打分表移除角色词，主体类只认主体属性词；② 类型切换改为"**严格优于当前上下文**才切换"（平局保持归属）。修复后该合同 6 条高风险全部命中 |
| 2 | 所有任务跑完都变 `blocked`，`block_code=PIPELINE_ERROR`，提示 `'module' object is not callable` | `run_review()` 内写了 `import json as _json`，**遮蔽了模块级的 `_json()` 函数**，导致后续 `_json(summary["focus_points"])` 调到了模块对象 | 局部 import 改名去掉，模块级统一 `import json`；同时给 `_json()` 补上明确实现 |
| 3 | 同一秒内创建两个任务报 `UNIQUE constraint failed: contracts.idem_key` | `gen_code()` 只精确到秒，同秒生成的编号相同 → 幂等键 `代码\|SHA256\|规则版本` 撞车 → 条件唯一索引冲突 | 编号末尾追加 4 位随机码；并补一条单元测试锁定该行为 |
| 4 | 幂等单元测试失败：首次创建就返回 `reused=true` | `app.config` 在 **import 时**就把 `HJ_DB` 读成常量。测试模块里再改 `os.environ` 已无效，测试直接写进了真实库，被 demo 留下的数据污染 | 新建 `conftest.py` 在**任何 `app.*` 导入之前**设置环境变量；并加模块级 `db.reset_db()` 隔离 |
| 5 | `GET /api/contracts/{id}/document` 返回 500：`name 'parser_docx' is not defined` | `api/contracts.py` 补导入时漏了 `parser_docx`（只导入了 `parser_pdf` / `parser_ocr`），而 `get_document()` 分支用到了它 | 补全导入；此类"漏导入"在冒烟里表现为 500，因此冒烟必须覆盖文档视窗接口 |

### 经验小结

| 教训 | 通用做法 |
| --- | --- |
| 分类器里放"高频无关词"会毁掉整条链路 | 特征词表要按**区分度**筛选，不要按"覆盖度"堆词 |
| 局部 import 可能与模块级命名冲突，且错误信息误导 | 模块级统一 import；避免 `import x as y` 后 `y` 与已有名字重名 |
| 用于幂等/唯一约束的 ID 不能用低精度时间戳 | 时间戳 + 随机后缀，或直接 UUID |
| 测试环境变量必须在导入被测模块前设置 | Python 项目统一放 `conftest.py` |
| 只要有一个接口没被冒烟覆盖，它就会是线上第一个 500 | 冒烟清单按**接口清单**逐条对账，不按"常用接口"挑 |
