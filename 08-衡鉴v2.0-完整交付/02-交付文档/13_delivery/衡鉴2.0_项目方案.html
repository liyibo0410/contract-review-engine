一 · 业务建模

审批人只有几分钟，却要读懂几十页合同

真实痛点从来不是「没有制度」，而是「人不够快、不够专、留不下痕」。

看不完
一份采购合同 30–60 页，逐条通读需 2 小时以上。
审批流卡在人身上，业务等不起。
看不准
风险藏在违约责任、争议管辖、知识产权等少数条款里。
缺一条验收前置条件，可能就是全款风险。
说不清
审批意见靠口头与批注，历史合同无法复盘。
出了纠纷，责任链断在半路。
问题定义

在不改变审批权责的前提下， 把「读合同、找风险、写意见」三步自动化，让审批人只做一件事 —— 做决定。

  • 边界：系统只生成审查意见、只写审批评论区；不提供通过 / 拒绝 / 转交 / 撤回等任何改变审批结论的动作。
  • 不做：不做合同起草、不做法务替代、不出具法律意见书。
  • 成功判据：每一条结论都能被逐字核对 —— 点到原文那一句、点到规则那一条、点到法条那一款。

三类目标用户

角色核心诉求关键成功标准
法务审查人快速定位风险、核对依据、出意见 从打开合同到出完意见 < 10 分钟；每条意见可回溯
业务经办人提交送审、知道哪里要改、拿到整改建议 首次送审即可看出风险点；能下载报告去跟对方谈判
系统管理员维护规则与模板、监控任务、处置阻塞 改规则后能立即验证是否改坏别的地方
一 · 问题建模与边界定义

谁有权下结论 —— 整套系统最重要的一条判断

不是「把合同丢给大模型」，而是明确划分：谁判定、谁表达、谁决定。

规则引擎（主路径）判定
有权：判定风险等级、给出命中项与原文坐标。

理由：同一份合同任何时候跑都必须得到同一份结论 —— 可复现才能被法务采信。
大模型（增强路径）表达
只做三件事：解释成因、润色示范条款、检测跨条款矛盾。

理由：这些恰恰是规则写不出来、而模型擅长的部分。超时或返回非法即降级。
法务审查人决定
决定：采纳或调整建议、补充批注、是否回写审批单。

系统的输出是「意见」，不是「结论」。
约束不是口号，是代码里的硬约束
  • LLM 的 Prompt 明确禁止新增 / 删除 / 合并风险项，禁止修改风险等级；
  • 输出必须通过结构校验，解析失败 / 超时 / 网络异常一律降级为确定性模板生成器；
  • 后端不存在任何改变审批结论的接口（无通过 / 拒绝 / 转交 / 撤回）。

支点一 · 统一坐标系（证据链的地基）

唯一真理坐标系 = 解析出的全文字符串。任何风险必须落到 [char_start, char_end) 区间； page / para_index 只是给人读的「人话定位」。

来源页码来源定位精度
DOCX识别 w:lastRenderedPageBreak 与显式分页符；无分页信息时如实退化为 page=1段落 + 字符区间
PDFPyMuPDF 页序号（天然真实）页 + 块 + 字符区间
扫描件OCR 行框按 (y, x) 还原阅读顺序行 + 字符区间

为什么这是壁垒：多数方案止步于「给出风险段落文字」。 而法务敢采信的前提，是能从结论一路点到原文那一句。它同时让前端只需一种高亮逻辑 就能支持三种格式。

不做什么：不估算页码，不伪造定位。 坐标取不到原文时标记为 -1，前端不渲染定位按钮 —— 假定位比没定位更危险。

支点二 · 视角解析（防误报的关键）

「知识产权归甲方所有」这句话，在采购合同里对我方有利， 在销售合同里对我方不利。 脱离视角的关键词匹配必然大面积误报。

业务类型我方对方说明
采购 / 服务 / 劳动甲方乙方需方 / 委托方 / 用人单位
销售乙方甲方卖方 / 供方

规则库用 {我方} / {对方} 占位书写，运行期按业务类型实例化。 另有三道配套闸门：biz_types（规则级适用范围，如"付款须挂钩验收"不适用于劳动合同）、 exclude_keywords（语境排除，如"累计不超过 20%"是上限保护而非比例风险）、 共现判定（付款与验收必须同句出现才算已绑定）。

支点三 · 双引擎与可降级（演示零事故）

外部依赖不可用时的行为用户损失
大模型接口超时（默认 8s）或返回非法 JSON → 切换确定性模板生成器 解释文字由模板拼装，结论与建议完全不变
OCR 引擎扫描件进入 blocked，阻塞原因明确写「引擎缺失」 提示安装依赖，其他格式不受影响

八种判定类型

类型语义为什么需要它
keyword关键词命中（any / all / none）覆盖绝大多数「明显违规表述」
regex正则匹配 + 语境排除处理「同一方 + 隔几个字 + 加重措辞」的句式
numeric数值阈值比对（多模式 + 排除设上限表述）违约金比例、预付款比例这类必须算数的问题
imbalance权责不对等（关键词版）简单配对场景
imbalance_regex权责不对等（正则版）只有跨句比较才能发现的不对等
missing_clause必备条款缺失「没写的」和「写错的」一样危险
required_combo条款组合缺失（共现 + 前提 + 反向排除）「有付款、没验收」这类组合缺陷
absent全篇缺少某项必要约定（支持前提条件）通知送达、金额大写、签署日期等要素级缺失
两个值得单说的判定难点
  • 跨句才能看出的不对等：
    甲方逾期支付款项的，应承担无限赔偿责任，并赔偿乙方因此遭受的一切损失。
    乙方逾期交付的，仅承担合同总价万分之一的违约金，且累计不超过合同总价。
    单看任一句都「语序通顺」，放在一起却是权责严重失衡 —— 用 imbalance_regex 表达「同一方 + 若干字符内 + 加重/减轻措辞」，并要求两者出现在同一违约责任章节内。
  • 「付款是否挂钩验收」不能全文搜索：质量保证条款里一句 「质保期为验收合格后 12 个月」会让全文搜索误以为"已有验收"，从而漏报付款环节根本没有验收前置的问题。 正确判据是共现：同一句里既是付款语境、 又出现验收语境，才算绑定。另用 require_exclude 处理否定语境 （「甲方无需另行支付任何经济补偿」不算满足）。

条款切分策略与踩坑记录

四步：① 标题正则识别 → ② 标题语义向下传播 → ③ 正文需 2 个关键词自证才允许切换类型 → ④ 切换要求严格优于当前上下文（平局保持归属）。

踩坑：条款词表里不能出现角色词

角色词（甲方 / 乙方 / 供方 / 需方）在合同里无处不在。 一旦计入打分，「本合同项下乙方为甲方定制开发形成的全部交付成果，其知识产权归乙方所有」 会被判成签约主体段而不是知识产权段 —— 整篇条款类型错位，连带基于 clause_type 的规则全部失效（首轮跑分召回率仅 45%）。

  • 修复一：角色词从打分表移除，主体类只认"主体属性词"（统一社会信用代码、法定代表人、营业执照、资质证书）；
  • 修复二：类型切换加"平局不动"规则。修复后该句正确判为 ip，HJ-H-001 恢复命中。

四 · 数据与接口

10 张表 · 33 个接口 · 5 态任务机 · 6 种阻塞码

HITL 用「动作流水」代替状态字段 —— 审计信息就是业务数据本身。

数据模型

表职责关键设计

状态机与阻塞码

任务： pending → parsing → reviewing → completed
                    └→ blocked（一键重试，清空重建，幂等键保留）

回写： not_written → writing → success / failed（保留错误与重试入口）
阻塞码触发条件为什么单独区分
DOC_ENCRYPTEDPDF 需要密码需去除密码，重试无意义
OCR_ENGINE_UNAVAILABLE扫描件且 OCR 未安装需装环境，不是文件问题
OCR_LOW_CONFIDENCE平均置信度 < 0.35需换清晰件
EMPTY_CONTENT正文 < 120 字可能是纯图片文档
PARSE_FAILED解析器异常需查审计日志
PIPELINE_ERROR流水线未预期异常需查 detail（含 traceback 片段）

「引擎缺失」与「图片模糊」必须分开记录 —— 否则用户只会反复点重试然后放弃。

人工审核（HITL）与回写安全边界

approve 同意
同意结论 → 解锁回写
edit 修改后确认
改等级 / 改写建议 → 自动重算综合等级与结论
reject 驳回
清空本次产物，任务回 pending 并重跑
resume 恢复
从阻塞中断点恢复，保留上下文
门禁：驳回后禁止回写

POST /writeback 返回 409，提示「请重新发起审查后再回写」。 两道校验：① 任务状态必须 completed；② 最后一次 HITL 动作不得为 reject。

回写四道保险
  • 只写评论：后端不存在任何审批结论写操作接口；
  • DRY_RUN 前置：回写前先生成待写入正文给你确认，预览模式只落库不外发；
  • 幂等三键：合同编号 | 附件 SHA256 | 规则版本号 —— 重复触发返回既有结果并记警告日志；
  • 审计闭环：每个步骤写 audit_logs，可从审查意见反查到完整处理链路。

三个值得单说的交互

  • 双向联动：点风险卡 → 左侧平滑滚动到原文那一段并高亮脉冲； 在原文划选一段话 → 弹出「片段研判」列出涉及的风险项。跨三种格式共用同一套逻辑。
  • 键盘流：j / k 切换风险项、 Enter 采纳、/ 聚焦检索 —— 这是给每天看几十份合同的人准备的。 焦点在输入框时除 Esc 外全部放行，避免写法务批注时误跳。
  • 实时进度：SSE 事件流带自增 seq， 支持断线续传；服务端空闲后主动关闭。Nginx 侧必须 proxy_buffering off， 否则事件会被积压成「进度条一直不动然后瞬间跳满」。

设计系统要点

深色底 #0B0E14 + 三级文字层次 + 风险三级色（红 #FF5D5D / 橙 #FFA93B / 灰 #7C8798）。 为什么用深色：这是长时间盯屏的工作界面而非展示页， 深色能降低阅读几十页合同正文的视觉疲劳，并让红色风险高亮「跳出来」。 为什么关键字段用等宽字体：规则编号、字符区间、幂等键 会被逐字符核对，等宽能显著降低看错一位的概率。 动效只用于表达状态变化，脉冲 1.1s × 2 次后消散，不留永久视觉噪音。

关于 100% 的诚实说明

黄金标注与规则库由同一团队同步编写。因此 100% 召回是 内部回归基线 —— 它的作用是防止「改一条规则、伤三处条款」， 不等于面对全新语料的泛化能力。

类比：单元测试全绿不代表程序没有 bug，只代表已写下的断言都成立。 「我们的规则在自建样例集上召回 100%」可验证； 「我们的系统能识别 100% 的合同风险」无法验证 —— 我们说前者。
