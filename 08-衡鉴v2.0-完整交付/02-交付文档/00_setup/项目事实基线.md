## 一、项目定位（一句话）

**让每一份合同，在审批前先过一遍"数字法务"的脑子 —— 风险可定位、依据可追溯、意见可回写。**

不改变审批权责：系统只生成审查意见、只写审批评论区，
**不提供通过 / 拒绝 / 转交 / 撤回等任何改变审批结论的动作**。

## 三、核心设计：统一坐标系（技术壁垒）

**唯一真理坐标系 = 解析出的全文字符串 `full_text`。**
任何一条风险记录都必须能落到 `full_text` 的 `[char_start, char_end)` 区间；
`page` / `para_index` 只是给人看的"人话定位"。

三种来源同构映射：

| 来源 | 页码来源 | 定位精度 |
| --- | --- | --- |
| DOCX | 识别 `w:lastRenderedPageBreak` 与显式分页符；无分页信息时如实退化为 page=1 | 段落 + 字符区间 |
| PDF | PyMuPDF 页序号（天然真实） | 页 + 块 + 字符区间 |
| 扫描件 | OCR 行框按 (y, x) 还原阅读顺序 | 行 + 字符区间 |

**为什么这是壁垒**：大多数方案止步于"给出风险段落文字"，
而**从风险到字符级定位的完整证据链**才是法务敢采信的前提，
也让前端只需要一种高亮逻辑就能同时支持三种格式。

## 四、确定性规则引擎（判定唯一来源）

**版本**：v1.0.0 ｜ **总数**：32 条 ｜ **高风险 11 / 中风险 13 / 低风险 8**
**示范条款库**：14 套

### 4.1 八种判定类型

| type | 语义 | 典型规则 |
| --- | --- | --- |
| `keyword` | 关键词命中（any / all / none 组合） | HJ-H-004 管辖约定在相对方所在地 |
| `regex` | 正则匹配（支持 exclude_keywords 排除语境） | HJ-H-008 我方单方无限责任 |
| `numeric` | 数值阈值比对（支持多模式 + 排除"设上限"表述） | HJ-H-006 违约金 >30% |
| `imbalance` | 权责不对等的关键词版 | —— |
| `imbalance_regex` | 权责不对等的正则版（同一方 + 若干字符内 + 加重/减轻措辞） | HJ-H-003 违约责任严重不对等 |
| `missing_clause` | 必备条款缺失 | HJ-H-009 缺失违约责任条款 |
| `required_combo` | 条款组合缺失（共现判定 + if_keywords 前提 + 反向排除） | HJ-H-002 付款缺少验收前置 |
| `absent` | 全篇缺少某项必要约定（支持 if_any 前提） | HJ-L-003 缺少通知送达条款 |

### 4.2 视角解析（防误报的关键设计）

> "知识产权归甲方所有"在采购合同里**对我方有利**，在销售合同里**对我方不利**。
> 脱离合同视角的关键词匹配必然大面积误报。

规则库用 `{我方}` / `{对方}` 占位书写，运行期按业务类型实例化：

| 业务类型 | 我方 | 对方 |
| --- | --- | --- |
| 采购 / 服务 / 劳动 | 甲方（需方／委托方／用人单位） | 乙方 |
| 销售 | 乙方（卖方／供方） | 甲方 |

另有 `biz_types` 规则级适用面控制：如"付款须挂钩验收"不适用于劳动合同。

### 4.3 高风险规则清单（11 条）

| ID | 标题 | 判定类型 |
| --- | --- | --- |
| HJ-H-001 | 知识产权归属相对方，我方未保留任何权利 | keyword |
| HJ-H-002 | 付款缺少验收前置条件（到货/交付即付全款） | required_combo |
| HJ-H-003 | 违约责任严重不对等 | imbalance_regex |
| HJ-H-004 | 争议管辖约定不当或约定在相对方所在地 | keyword |
| HJ-H-005 | 相对方主体信息缺失或存在经营异常 | keyword |
| HJ-H-006 | 违约金比例超出法定合理范围（>30%） | numeric |
| HJ-H-007 | 预付款比例过高且未约定担保或对价保障（≥50%） | numeric |
| HJ-H-008 | 我方单方承担无限责任或无赔偿上限 | regex |
| HJ-H-009 | 缺失违约责任条款 | missing_clause |
| HJ-H-010 | 缺失争议解决与管辖条款 | missing_clause |
| HJ-H-011 | 竞业限制未约定经济补偿（劳动类） | required_combo |

中风险 13 条：HJ-M-001~013（保密无期限、不可抗力无通知时效、缺知识产权条款、
缺数据安全条款、缺交付验收标准、违约金 15–30%、付款表述模糊、交付期限模糊、
保密单向、有效期未明确、缺不可抗力、争议仅约定协商、未要求资质证明）
低风险 8 条：HJ-L-001~008（发票安排、合同份数与附件效力、通知送达、金额大写、
签署日期、法定代表人署名、书面变更、履约进度沟通）

### 4.4 十一条条款本体树（clause_type）

`subject` 签约主体与资质 ｜ `subject_matter` 标的物 ｜ `payment` 价款与支付 ｜
`delivery` 交付与验收 ｜ `liability` 违约责任 ｜ `confidentiality` 保密义务 ｜
`ip` 知识产权 ｜ `data_security` 数据安全 ｜ `dispute` 争议解决与管辖 ｜
`validity` 合同效力 ｜ `force_majeure` 不可抗力 ｜ `other` 其他

**条款切分策略**：标题正则识别 → 标题语义向下传播 → 正文需 2 个关键词自证才允许切换类型
→ 切换要求**严格优于当前上下文**（平局保持归属）。
*踩坑记录*：角色词（甲方/乙方）一旦计入打分，会把"知识产权段"判成"签约主体段"，
连带整篇风险命中失效 —— 因此条款词表中刻意不含角色词。

| 表 | 关键字段 | 说明 |
| --- | --- | --- |
| `contracts` | code, name, applicant, dept, biz_type, counterparty, uscc, amount, currency, status, risk_level, conclusion, block_code, block_reason, idem_key, meta_json, profile_json | 合同/任务主表，`idem_key` 唯一索引 |
| `documents` | contract_id, file_name, file_type, sha256, parse_engine, parse_status, page_count, char_count, ocr_confidence | 附件与解析状态 |
| `clauses` | document_id, contract_id, clause_type, page, para_index, char_start, char_end, text | 条款结构树（锚定基础） |
| `findings` | contract_id, rule_id, rule_version, level, clause_type, judge_mode, evidence_text, page, char_start, char_end, reason, legal_basis, advice, advice_source, adopted, adopted_text | 风险命中（证据链核心） |
| `reviews` | risk_summary, conclusion, focus_points, high_cnt, medium_cnt, low_cnt, reviewer_note, generated_by, rule_version | 审查意见 |
| `writebacks` | status, dry_run, idem_key, attempt, payload_md, platform_comment_id, error, operator | 回写状态机 |
| `audit_logs` | contract_id, step, tool, level, input_digest, output_digest, cost_ms, detail | 全链路留痕 |
| `eval_runs` | rule_version, total_cases, parse_ok, high_total, high_hit, high_recall, false_positive, precision, avg_ms, verdict, detail_json | 评测历史 |
| `platform_comments` | contract_id, writeback_id, author, body_md, kind | 审批系统评论区（内置模拟器） |
| `hitl_actions` | contract_id, action, actor, note, interrupt_at, payload_json | 人工审核动作流水（approve/edit/reject/resume），当前状态由最后一条推出 |

**为什么 HITL 落"动作流水"而不落"状态字段"**：谁在什么时候同意/修改/驳回了什么，
天然可追溯 —— 审计信息就是业务数据本身，不需要额外维护状态迁移日志。
`hitl_actions` 与 `audit_logs` 的分工是：前者记录**业务决策**，后者记录**系统执行**。

## 六、状态机

### 6.1 任务状态

```
pending ──► parsing ──► reviewing ──► completed
   ▲            │            │
   └──── blocked ◄───────────┘
        （一键重试 → 回到 pending，清空 clauses/findings/reviews，幂等键保留）
```

### 6.2 回写状态

```
not_written ──► writing ──► success
                    └────► failed（保留错误信息与重试入口）
```

### 6.3 人工审核（HITL）中断点与动作

与 LangGraph 的 `interrupt` 语义对齐：中断点不是"报错"，
而是**流程主动停下来等人做决定**的位置，因此必须给出可执行的下一步动作。

| 中断点 | 触发条件 | 可执行动作 |
| --- | --- | --- |
| `parsing` | 任务 `blocked` | `resume`（从阻塞恢复，保留中断上下文） |
| `reviewing` | 审查完成，等待法务确认 | `approve` / `edit` / `reject` |
| `reviewing` | 审查结果已被驳回 | 无（需重新跑流水线） |
| `applying` | 已确认，等待回写 | `reject`（撤回确认） |
| —— | 流水线运行中（pending/parsing/reviewing） | 无（无需人工介入） |

| 动作 | 语义 | 系统行为 |
| --- | --- | --- |
| `approve` | 同意系统审查结论 | 记录流水，解锁回写 |
| `edit` | 修改风险等级 / 改写建议后确认 | 更新 `findings`，重算综合风险等级与审查结论，`reviews.generated_by` 标记 `human_edited` |
| `reject` | 驳回审查结果 | 清空本次 findings/reviews，任务回到 `pending` 并自动重跑 |
| `resume` | 从阻塞中断点恢复 | 等价于 retry，但保留中断上下文 |

**门禁**：审查结果被驳回后，回写接口返回 409 —— 必须先重新审查。

### 6.4 阻塞代码（六种，必须可读且可区分）

| 代码 | 触发条件 | 处理建议 |
| --- | --- | --- |
| `DOC_ENCRYPTED` | PDF 需要密码 | 上传去除密码的版本 |
| `OCR_ENGINE_UNAVAILABLE` | 扫描件且 OCR 引擎未安装 | 安装 rapidocr-onnxruntime |
| `OCR_LOW_CONFIDENCE` | 平均置信度 < 0.35 | 重新上传清晰扫描件 |
| `EMPTY_CONTENT` | 正文 < 120 字 | 检查文档是否为纯图片无文字 |
| `PARSE_FAILED` | 解析器异常 | 查看审计日志定位 |
| `PIPELINE_ERROR` | 流水线未预期异常 | 查看 audit_logs 的 detail |

**设计要点**："引擎缺失"与"图片模糊"必须分开记录 —— 否则重试没有意义。

### 7.4 统一响应约定

- 成功：业务对象直接返回（不使用 `{code,data,msg}` 包装 —— 由 HTTP 状态码表达结果）
- 失败：`{"detail": "可读中文原因"}`，状态码 400 / 404 / 409 / 413 / 500
- 所有响应头带 `X-Process-Time-Ms` 与 `X-HengJian-Version`
- SSE 事件格式：`data: {"seq","contract_id","stage","message","progress","level","ts","extra"}`

## 九、审批回写安全边界（工程红线）

1. **只写评论** —— 后端不存在任何审批结论写操作接口；
2. **DRY_RUN 前置** —— 回写前先生成待写入正文，预览模式只落库不外发；
3. **幂等三键** —— `合同编号 | 附件 SHA256 | 规则版本号`，重复触发返回既有结果并记 `writeback.skip` 警告日志；
4. **状态机兜底** —— 任何下游异常落到 `failed`，保留错误与重试入口；
5. **审计闭环** —— 每个步骤写 `audit_logs`（step / tool / input_digest / output_digest / cost_ms），
   可从审查意见反查到完整处理链路。

## 十三、写作规范（所有文档必须遵守）

1. **中文写作**，技术标识符保留英文原文；
2. 文档开头必须有「**一句话结论**」，让读者 10 秒内知道这篇讲什么；
3. 表格优先于长段落；每个关键设计都要写**为什么这么做**，而不是只写做了什么；
4. 禁止使用"赋能、闭环、抓手、打法"这类空话；用具体数字与可验证的断言；
5. **不得编造数字**。所有指标只能引用本文件第八章；
6. 涉及"未实现"的能力必须显式标注 **【未开发】**，禁止伪造功能；
7. 每篇文档末尾附「**相关文档**」交叉引用列表。
