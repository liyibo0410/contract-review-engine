## 一、为什么要有一套"规则体系"而不是一堆提示词

合同审查的结论要**可解释、可复核、可追溯、可审计**。大模型的自由判断无法同时满足这四条：

| 要求 | 规则引擎 | 大模型直判 |
| --- | --- | --- |
| 可复现（同一输入同一输出） | ✅ 确定 | ❌ 受温度、上下文、模型版本影响 |
| 可解释（为什么判为风险） | ✅ 规则 ID + 参数 + 法条 | ⚠️ 事后编解释，可能与判定逻辑不符 |
| 可追溯（结论改了几版） | ✅ YAML 版本号 + git | ❌ 无版本概念 |
| 可审计（谁改的、影响面） | ✅ 规则级粒度 | ❌ 全量重跑才知道 |

因此本系统的分工是：**规则引擎下判定，大模型做表达**。
大模型的 Prompt 中明确禁止新增/删除/合并风险项，禁止修改风险等级，输出必须过结构校验。

## 二、判定类型体系（8 种）

| # | type | 语义 | 判定要素 | 代表规则 |
| --- | --- | --- | --- | --- |
| 1 | `keyword` | 关键词命中 | `any` / `all` / `none` 三种条件的组合 | HJ-H-004 管辖约定在相对方所在地 |
| 2 | `regex` | 正则匹配 | `pattern` + `exclude_keywords`（语境排除） | HJ-H-008 我方单方无限责任 |
| 3 | `numeric` | 数值阈值比对 | `patterns`（多模式）+ `op` + `threshold` + `exclude_keywords` | HJ-H-006 违约金 >30% |
| 4 | `imbalance` | 权责不对等（关键词版） | `heavy` / `light` 措辞对 + `window` | —— |
| 5 | `imbalance_regex` | 权责不对等（正则版） | `heavy_patterns` / `light_patterns` + `window` | HJ-H-003 违约责任严重不对等 |
| 6 | `missing_clause` | 必备条款缺失 | `clause_type` + `rescue_keywords`（关键词兜底） | HJ-H-009 缺失违约责任条款 |
| 7 | `required_combo` | 条款组合缺失 | `if_clause_type` + `if_keywords` + `cooccur_keywords` + `require_keywords` + `require_exclude` | HJ-H-002 付款缺少验收前置 |
| 8 | `absent` | 全篇缺少某项必要约定 | `if_any`（前提）+ `none`（必须缺失的约定） | HJ-L-003 缺少通知送达条款 |

### 2.1 为什么必须有 `imbalance_regex`

真实合同里的不对等，措辞往往是这样写的：

```
甲方逾期支付款项的，应承担无限赔偿责任，并赔偿乙方因此遭受的一切损失。
乙方逾期交付的，仅承担合同总价万分之一的违约金，且累计不超过合同总价。
```

单独看任何一句都"语序通顺"，但**放在一起就是权责严重失衡**。
纯关键词列表匹配不到（"甲方"与"承担无限"之间隔着"逾期支付款项的，应"9 个字），
所以用正则表达"**同一方 + 若干字符内 + 加重/减轻措辞**"，
并要求加重句与减轻句出现在同一违约责任章节内（`window` 控制句距）。

### 2.2 为什么必须有 `required_combo` 的共现判定

"付款是否挂钩验收"这个问题，用"全文搜索"会**漏报**：

```
第二条 合同金额与付款
  甲方应在收到货物后 60 日内一次性支付全部货款。
第五条 质量保证
  乙方保证质保期为验收合格后 12 个月。   ← 全篇确实出现"验收合格"，但它不管付款
```

正确判据是**共现**：只有同一句话里既出现付款语境、又出现验收语境，才算"付款已挂钩验收"。
另外 `require_exclude` 处理否定语境 —— 劳动合同里写"甲方**无需**另行支付任何经济补偿"，
虽然句中出现"经济补偿"，但被否定，不算满足。

## 三、十一条条款本体树与切分策略

`subject` 签约主体与资质 ｜ `subject_matter` 标的物 ｜ `payment` 价款与支付 ｜
`delivery` 交付与验收 ｜ `liability` 违约责任 ｜ `confidentiality` 保密义务 ｜
`ip` 知识产权 ｜ `data_security` 数据安全 ｜ `dispute` 争议解决与管辖 ｜
`validity` 合同效力 ｜ `force_majeure` 不可抗力 ｜ `other` 其他

### 切分四步

1. **标题识别**：正则匹配 `第X条` / `一、` / `数字.` / `【小标题】` 等形态；
2. **语义传播**：标题决定其后正文的条款类型（真实合同的正文往往不含"违约责任"字样，但整条都在讲违约责任）；
3. **自证切换**：正文需命中 **≥2 个**该类型关键词才允许切换上下文（单个关键词太容易误判）；
4. **平局保序**：切换要求**严格优于当前上下文得分**，平局保持归属。

### 踩坑记录（值得写进规范）

> **条款词表里不能出现角色词（甲方 / 乙方 / 供方 / 需方）。**

角色词在合同里无处不在（几乎每段都会提到双方）。一旦计入打分，
"本合同项下乙方为甲方定制开发形成的全部交付成果，其知识产权归乙方所有"
会被判成**签约主体段**而不是**知识产权段** —— 整篇条款类型错位，
连带基于 `clause_type` 的风险规则全部失效。

**修复**：角色词从打分表移除，主体类判定只认"主体属性词"
（统一社会信用代码、法定代表人、营业执照、资质证书……）；
同时给类型切换加上"平局不动"规则。
修复后该句正确判为 `ip`，HJ-H-001 恢复命中。

## 四、视角解析：防误报的核心机制

### 4.1 问题

| 合同类型 | 文本 | 对我方 | 应否报高风险 |
| --- | --- | --- | --- |
| 采购（我方=甲方） | 知识产权归**乙方**所有 | 不利 | ✅ 报 |
| 销售（我方=乙方） | 知识产权归**甲方**所有 | 不利 | ✅ 报 |
| 采购（我方=甲方） | 知识产权归**甲方**所有 | 有利 | ❌ 不报 |

同一句话在不同视角下结论完全相反。**脱离视角的关键词匹配必然大面积误报。**

### 4.2 方案

规则库用 `{我方}` / `{对方}` 占位书写，运行期按业务类型实例化：

| 业务类型 | 我方 | 对方 |
| --- | --- | --- |
| 采购 / 服务 / 劳动 | 甲方（需方／委托方／用人单位） | 乙方 |
| 销售 | 乙方（卖方／供方） | 甲方 |

示例规则（HJ-H-001 知识产权归属相对方）：

```yaml
params:
  any:
    - "知识产权归{对方}所有"
    - "著作权归{对方}所有"
    - "成果所有权归{对方}"
  none:
    - "双方共有"
    - "共同所有"
    - "{我方}保留"
```

### 4.3 三道配套闸门

| 闸门 | 作用 | 示例 |
| --- | --- | --- |
| `biz_types` | 规则适用面控制 | "付款须挂钩验收" 仅 `["采购","服务"]`，劳动合同不适用 |
| `exclude_keywords` | 语境排除 | "累计**不超过**合同总价的 20%" 是上限保护，不算违约金比例风险 |
| `cooccur_keywords` + `require_exclude` | 共现 + 否定 | 见 §2.2 |

## 七、评测报告

### 7.1 指标口径与 RAGAS 的对应关系

本系统的主判定路径是**确定性规则引擎**而非向量检索，
因此这里实现的是"面向规则系统的检索式评测"，
同时保留 RAGAS 的四项核心指标口径以便横向对照：

| RAGAS 指标 | 原始含义（RAG 场景） | 本项目的对应实现 |
| --- | --- | --- |
| **Context Recall** | 检索到的上下文覆盖参考答案的比例 | **高风险召回率** = 黄金标注中被命中的高风险规则数 / 黄金标注高风险总数 |
| **Context Precision** | 检索结果中相关项的占比 | **准确率 Precision** = 命中的高风险中真正期望的占比 |
| **Faithfulness** | 回答是否忠实于检索上下文 | **裁定模式约束**：LLM 输出必须引用规则命中的 `rule_id`，不得新增风险项；越界即校验失败并降级 |
| **Answer Relevancy** | 回答与问题的相关度 | **建议可落地性**：每条高风险必须带标准示范条款（校验项：`legal_basis` 与 `advice` 均非空） |
| **——** | —— | 额外补充 **解析成功率** 与 **平均解析耗时**（工程可用性指标） |

> **为什么做这个映射**：RAGAS 是面向检索增强生成的评价框架，
> 直接套用到规则引擎上会得出"没有检索、无法评价"的错误结论。
> 正确的做法是**对齐指标语义**（都回答"该找的找到了吗 / 不该报的报了吗"），
> 而不是对齐工具名字。

### 7.4 ⚠️ 关于 100% 的诚实说明（必须原样引用）

> **黄金标注与规则库由同一团队同步编写。**
> 这意味着 100% 召回是**内部回归基线**，它的作用是**防止"改一条规则、伤三处条款"**，
> **不等于**面对全新语料的泛化能力。
>
> 一个诚实的类比：单元测试全绿不代表程序没有 bug，只代表已写下的断言都成立。
> 同理，"我们的规则在自建样例集上召回 100%"是一句可验证的真话，
> 而"我们的系统能识别 100% 的合同风险"是一句无法验证的假话 —— **我们说前者**。

**补上泛化能力的路径**（已列入路线图 M2）：

| 步骤 | 做法 |
| --- | --- |
| 1 | 采集 50–100 份真实合同（脱敏），覆盖更多业务类型与排版风格 |
| 2 | 由**未参与规则编写**的法务人员独立标注风险清单（盲测） |
| 3 | 在盲测集上跑分，公开**真实的**召回率与误报率（预期会低于 100%，这是正常的） |
| 4 | 按漏报/误报聚类，定向补充与收紧规则，形成"标注 → 跑分 → 调优"闭环 |

## 八、规则变更的工程约束

规则库不是"文档"，是**代码**。因此：

| 约束 | 落地方式 |
| --- | --- |
| 变更可追溯 | YAML 内 `version` 字段 + git 历史；每次修改需同步升级版本号 |
| 变更可验证 | 修改后必须重跑黄金集；CI 门禁三会**断言**召回率与误报数 |
| 变更可审计 | 规则编辑接口写 `audit_logs`（谁在何时改了哪条规则） |
| 引用完整性 | CI 门禁一校验 `advice_ref` 指向的示范条款必须存在 |
| 结构合法性 | CI 门禁一校验规则 ID 唯一、数量 ≥30、判定类型在白名单内 |

```bash
# 改完规则后的标准动作
cd backend
python -m app.eval.run_eval        # 1. 跑分
python -m pytest -q                # 2. 单测（含 6 种判定类型的针对性用例）
git diff app/rules/rules_v1.yaml   # 3. 人工复核 diff
```

## 九、标准示范条款库（14 套）

示范条款是"可直接写进合同、要承担法律后果"的文本，
因此**以标准库为底稿、LLM 只做措辞调整**，而不是让模型凭空生成。

| 类型 | 套数 | 示例 |
| --- | --- | --- |
| 知识产权 | 1 | T-IP-001 区分既有 IP 与定制成果，定制成果归我方 + 侵权兜底 |
| 价款支付 | 2 | T-PAY-001 里程碑付款 + 验收前置；T-PAY-002 预付款与担保对等 |
| 违约责任 | 3 | T-LIA-001 对等违约责任含 20% 上限；T-LIA-002 违约金合理区间；T-LIA-003 赔偿上限与除外 |
| 争议解决 | 1 | T-DIS-001 管辖地约定（我方所在地优先） |
| 签约主体 | 1 | T-SUB-001 主体资质与签署权限 |
| 保密义务 | 2 | T-CON-001 双向保密含 3 年期限；T-CON-002 竞业限制含经济补偿 |
| 不可抗力 | 1 | T-FOR-001 通知时效 + 证明文件 + 超期解除权 |
| 数据安全 | 1 | T-DAT-001 最小必要处理 + 24 小时通知 + 责任排除在限额外 |
| 交付验收 | 1 | T-DLV-001 交付验收标准指向可测量附件 |
| 合同效力 | 1 | T-VAL-001 生效、份数、书面变更、送达地址四条一次补齐 |

每套模板附带 `note` 字段写明**谈判要点**，与外部接口 `GET /api/templates/{id}` 的
`used_by_rules` 反向引用配合，修改模板前可先看清影响面。
