# 衡鉴 2.0 · 上传与解析链路（交互设计）

> **一句话结论**：上传入口接受 DOCX/PDF/扫描件及纯文本，**30MB 上限**；创建任务时以"合同编号 + 附件 SHA256 + 规则版本号"做幂等去重，相同附件直接复用既有任务而不重复解析。

---

## 一、上传入口

上传发生在两个位置，后端统一走 `POST /api/contracts/upload`：

| 入口 | 页面 | 说明 |
| --- | --- | --- |
| 大盘拖拽 / 点击上传 | `index.html` 审查大盘「接入合同」卡片 | 支持拖拽与点击；可填合同名称、申请人、送审部门、业务类型（默认自动识别） |
| 从审批系统拉取 | 大盘「从审批系统拉取待办任务」按钮 | `POST /api/contracts/pull` 内置模拟器，按顺序读取 `samples/` 目录生成待审任务 |

参数（multipart / Form）：

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| `file` | 是 | 合同文件本体 |
| `name` | 否 | 合同名称，留空则取文件名 stem |
| `applicant` | 否 | 申请人 |
| `dept` | 否 | 送审部门 |
| `biz_type` | 否 | 默认 `other`（自动识别）；可选 采购/销售/服务/劳动 |
| `auto_run` | 否 | 默认 `true`，上传后立即后台跑流水线 |

---

## 二、文档校验

后端在写入前做两类校验，**全部返回可读中文 `detail`**，不使用包装体。

### 2.1 类型校验

实际接受后缀（以代码 `contracts.py` 为准，比基线"DOCX/PDF/扫描件"描述更宽）：

```
.docx .pdf .png .jpg .jpeg .bmp .tif .tiff .txt .md
```

> ⚠️ **与基线头条表述的差异修正**：基线第二章技术栈写"文档解析：python-docx / PyMuPDF / RapidOCR"，给人"只支持三种来源"的印象；但 `upload` 接口实际还放行 `.txt/.md/.bmp/.tif/.tiff`，其中 `.txt/.md` 走 `plaintext` 引擎、`.bmp/.tif/.tiff` 走 OCR 路径。本文以代码为准。

不支持的后缀 → **HTTP 400**，`detail="不支持的文件类型：{suffix}"`。

### 2.2 大小校验

- 上限来自 `HJ_MAX_UPLOAD_MB`，**默认 30MB**。
- 流式读取，边读边累计；一旦超过上限立即删除临时文件并抛 **HTTP 413**，`detail="文件超过 30MB 上限"`。
- 为什么边读边判：避免先把整个大文件落盘再报错，浪费 IO 与磁盘。

### 2.3 空文件

文件名缺失 → 400；正文空内容（解析后 `<120` 字）不在此步拦截，而是进入解析阶段由阻塞码 `EMPTY_CONTENT` 处理（见 `02_中间状态与异常.md`）。

## 三、任务创建

`pipeline.create_task` 的职责：

1. 计算附件 **SHA256** 与当前**规则版本号** `rule_engine.rule_version()`；
2. 生成任务编号 `HJ-YYYYMMDD-HHMMSS-XXXX`（末尾 4 位随机，参与幂等键，防同秒撞车）；
3. 构造**幂等键** `idem_key = 合同编号 | 附件SHA256 | 规则版本号`；
4. 持久化 `contracts`（状态 `pending`）与 `documents`（解析状态 `pending`）；
5. 写 `audit_logs` 的 `task.create`，返回 `{contract_id, code, reused, sha256}`。

---

## 四、幂等去重（三键）

**为什么需要幂等**：审批系统可能重复推送同一份合同；演示中"从审批系统拉取"也会重复点。若每次都新建任务重跑，会污染大盘统计、产生重复回写。

| 幂等键组成 | 来源 | 作用 |
| --- | --- | --- |
| 合同编号 `code` | 上传时生成 | 任务在审批系统中的映射 ID |
| 附件 SHA256 | 文件指纹 | 识别"同一份文件" |
| 规则版本号 | `rules_v1.yaml` 版本 | 规则变了，旧审查结果应失效，允许重跑 |

**去重逻辑**：若 `documents.sha256` 已存在且非 `force_new`，则返回既有任务 `reused=true`，**不新建、不重跑**，并向前端发 `idempotent` 事件提示"复用既有审查任务"。

> 注意：去重以 SHA256 为准，不以文件名/编号为准——同一文件改名上传仍会被识别为复用。

---

## 五、解析任务创建

`auto_run=true` 且非复用 → 调用 `pipeline.run_pipeline_async`，后台线程启动完整流水线（解析 + 审查），**立即返回**给前端，前端通过 SSE 看实时进度（见 `02_中间状态与异常.md`）。

若 `auto_run=false`，仅创建 `pending` 任务，等待前端手动 `POST /{id}/pipeline` 触发。

---

## 六、返回结构与前端应做什么

### 6.1 `/upload` 返回（200）

```json
{
  "contract_id": 17,
  "code": "HJ-20260919-110000-ab12",
  "reused": false,
  "sha256": "e3b0c4...",
  "auto_run": true,
  "message": "任务已创建，正在后台解析与审查"
}
```

| 字段 | 前端动作 |
| --- | --- |
| `reused=true` | 提示"已复用既有任务"，直接跳到该任务工作台，不要再等进度 |
| `auto_run=true` | 跳到工作台并订阅 `/{id}/events` SSE，展示实时进度条与时间轴 |
| `reused=false & auto_run=false` | 进入待处理态，等待用户手动触发流水线 |

### 6.2 错误返回

| 状态码 | 含义 | 前端应展示 |
| --- | --- | --- |
| 400 | 类型不支持 / 缺文件名 | 红色 toast："{detail}"，不上传 |
| 413 | 超过 30MB | 红色 toast 提示超限，引导压缩或换文件 |
| 500 | 服务异常 | 通用错误态，引导重试 |

### 6.3 大盘列表同步

上传成功后前端调用 `/api/contracts` 刷新列表，并按 `contract_id` 选中新任务；若处于 `pending/parsing/reviewing` 则自动订阅 SSE（大盘 `selectTask` 已实现该逻辑）。
