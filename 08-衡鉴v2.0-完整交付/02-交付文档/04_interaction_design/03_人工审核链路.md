# 衡鉴 2.0 · 人工审核链路（HITL，交互设计）

> **一句话结论**：人工审核四类动作 `approve / edit / reject / resume` 都写入 `hitl_actions` 流水（天然可追溯）；`reject` 与"非 completed 态"会触发 409 门禁，保证被驳回的审查结果无法回写、必须重跑。

---

## 一、动作总览与前置条件

接口：`POST /{id}/human-review`，统一响应 `{ok, hitl_id, action, applied, interrupt_at, message}`；非法动作 → **400**。

| 动作 | 语义 | 前置条件（不满足即返回错误码） | 触发的中断点 |
| --- | --- | --- | --- |
| `approve` | 同意系统结论 | 任务必须 `completed`，否则 **409**（"尚无审查结果可供确认"） | `reviewing` → `applying` |
| `edit` | 改级/改写建议后确认 | 任务必须 `completed`，否则 **409**；`edits` 非空，否则 **400** | `reviewing` → `applying` |
| `reject` | 驳回审查结果 | 任务必须 `completed`，否则 **409**（"无可驳回的审查结果"） | 回到 `pending` 重跑 |
| `resume` | 从阻塞中断点恢复 | 任务必须 `blocked`（否则无可恢复） | `parsing` 重试 |

> 为什么 `approve/edit` 必须 `completed`：只有审查跑完才有"结论"可供确认；`pending/parsing/reviewing` 阶段系统认为"流水线运行中，无需人工介入"，`_available_actions` 直接返回空。

---

## 二、approve 链路

**后端行为**
1. 校验 `status==completed`（否则 409）。
2. 仅向 `hitl_actions` 写一条 `action=approve`（含 actor、note、interrupt_at）。
3. 不改变 findings / reviews / 风险等级——`approve` 只是"解锁回写"的决策。
4. `GET /{id}/hitl` 此时 `writeback_allowed=true`，回写接口不再被门禁拦截。

**前端交互**
- 弹窗「确认审查结论」：一行说明"确认后该审查结果允许写回审批系统" + 可选审核意见 `textarea` + 取消/确认同意。
- 确认回调 `submitHitl('approve', note, [])`，成功后 toast + 刷新工作台并切到"结论与回写"页。

---

## 三、edit 链路（改判 + 改写建议）

**后端行为**
1. 校验 `status==completed`、`edits` 非空（否则 400/409）。
2. 逐条 findings 应用修改：
   - `level ∈ {high,medium,low}` → 更新 `level`；
   - `advice` 非空 → 更新 `advice` 与 `advice_source='manual'`；
   - `adopted` → 更新采纳态。
3. **重算**综合风险等级与计数：按 findings 重新分组计数，写回 `reviews.high_cnt/medium_cnt/low_cnt`，`generated_by='human_edited'`。
4. 重算 `risk_level`（有高→high，否则有中→medium，否则有低→low，否则 none）。
5. 重算 `conclusion`：高→"建议拒绝"、中→"建议整改后通过"、低/无→"建议通过"。
6. 写 `hitl_actions`（`action=edit`，payload 记录 applied 清单）。

**为什么重算**：人工改级后，大盘的风险色块、结论文案必须与明细一致，否则会出现"明细改了高风险、大盘还显示建议通过"的失真。

**前端交互**
- 弹窗「人工修改审查结果」：每条风险一行——等级下拉（保持/高/中/低）+ 系统建议 `textarea`（可改）。底部"修改说明" `textarea`。
- 点击"应用修改"时，前端逐条比对：等级被改或建议文本与原文不同才纳入 `edits`。
- **必填校验**：若没有任何改动 → toast「没有检测到修改」并阻断提交；否则 `submitHitl('edit', note, edits)`。

---

## 四、reject 链路（驳回 + 重跑）

**后端行为**
1. 校验 `status==completed`（否则 409）。
2. 清空本次审查产物：`DELETE FROM findings`、`DELETE FROM reviews`。
3. `_update_task`：状态回 `pending`，`risk_level='none'`、`conclusion=''`、`risk_summary=''`、清 `block_code/block_reason`。
4. 写 `hitl_actions`（`action=reject`，note 记录驳回理由）。
5. 立即 `pipeline.run_pipeline` 重新跑（与 retry 同语义：清空 clauses/findings/reviews 后重跑，回写记录保留）。

**前端交互**
- 弹窗「驳回审查结果」：
  - 黄色 warn banner："驳回将清空本次审查结果，任务回到「待处理」，需重新跑一遍流水线。请确认系统结论确实存在实质错误。"
  - **必填**：驳回理由 `textarea`（占位"例如：第 5 条付款安排已在本合同附件中另行约定，不构成风险"）。
  - 确认回调前校验：理由为空 → toast「请填写驳回理由」并阻断。
- 提交后任务回到 `pending`，前端自动重新订阅 SSE 看重跑进度。

---

## 五、resume 链路（从阻塞恢复）

**后端行为**
1. 仅当 `status==blocked` 可用（`_available_actions` 对 blocked 返回 `["resume"]`）。
2. 等价于 `pipeline.retry`：清历史 clauses/findings/reviews，状态回 `pending`，重跑流水线；幂等键与回写记录保留。
3. 写 `hitl_actions`（`action=resume`）。

**前端交互**：无弹窗（或仅带既有批注），直接 `submitHitl('resume', note, [])`；工作台 `renderBlocked` 的"重新解析/重试"按钮即走此路径。

## 六、门禁：驳回后回写被 409 拦截

回写接口 `POST /{id}/writeback` 有两道 409 门禁（代码 `contracts.py`）：

```python
if c["status"] != "completed":
    raise 409 "任务尚未审查完成（当前状态 {status}），不可回写"
last = _last_hitl(contract_id)
if last and last["action"] == "reject":
    raise 409 "审查结果已被驳回，请重新发起审查后再回写"
```

| 场景 | 结果 | 用户看到 |
| --- | --- | --- |
| `completed` 且未驳回 | 允许回写 | 正常写回评论区 |
| 非 `completed`（含 pending/parsing/reviewing/blocked） | 409 第一道 | "任务尚未审查完成，不可回写" |
| `completed` 但最后动作为 `reject` | 409 第二道 | "审查结果已被驳回，请重新发起审查后再回写" |

**设计意图**：驳回意味着"系统这次结论不可信"，若仍允许回写会把错误意见写进审批单。**门禁把"重跑"设为回写的前置**，从接口层杜绝脏数据外发。即使前端漏做禁用，后端 409 也能兜底。

> 注意：reject 后任务已回到 `pending`（非 completed），两道 409 都会拦；第二道用 `reject` 文案更明确地指引用户"先重跑审查"。

## 七、前端 HITL 状态映射

`GET /{id}/hitl` 返回 `status` 与 `available_actions`，工作台据此渲染按钮：

| hitl.status | 含义 | 展示按钮 |
| --- | --- | --- |
| `pending_review` | 审查完成待确认 | 同意 / 修改后确认 / 驳回 |
| `approved` | 已确认 | 驳回（撤回确认） |
| `edited` | 已修改确认 | 驳回 |
| `rejected` | 已驳回 | 无（需重跑） |
| `blocked` | 解析受阻 | 从阻塞恢复 |

`writeback_allowed` 同时为 `success` 或 `completed` 且未被 reject 时为真——这是回写按钮可用性的权威来源。
