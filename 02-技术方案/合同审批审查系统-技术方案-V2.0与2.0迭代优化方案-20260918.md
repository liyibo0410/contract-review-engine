# 第一部分 · 技术方案 V2.0（修订版）

## 一、修订说明

### 1.1 为什么必须修订

技术方案 V1.0 在第四节「目录结构」与第三节「技术选型」中承诺的 FastAPI + Jinja2 + PyMuPDF + RapidOCR +
reportlab + uv 技术栈，**与实际交付物存在 9 项技术栈级偏离**（详见评审意见书 R-04）。
根因是老师标注的交付约束「不带依赖、不含 venv」与 V1.0 的选型正面冲突——实现阶段服从了硬约束，
方案却未同步修订，形成「方案说 A、交付是 B」的文档性风险。

**本次修订原则：以已交付并已验证的零依赖实现为基线重写方案，方案对齐实现。**
V1.0 中列明的依赖栈不作废，转入附录作为「可选生产化升级路径」保留。

### 1.2 V1.0 → V2.0 主要变更

| # | 维度 | V1.0 | V2.0（本次修订） |

## 二、总体架构

系统按「接入 → 解析 → 抽取 → 审查 → 推荐 → 回写 → 展示」七段链路组织，前后端**同进程**部署，数据落 SQLite。

## 三、技术选型（零依赖基线）

| 层次 | 选型 | 理由 |
| --- | --- | --- |
| Web 服务 | 标准库 `http.server.ThreadingHTTPServer` | 零依赖；HTTP/1.1 + 显式 `Content-Length`；支持 gzip 与安全响应头 |
| 前端 | 原生 HTML/CSS/JS（ES Module） | 无框架、无构建、无 CDN；断网可演示，交付即可跑 |
| 存储 | 标准库 `sqlite3` | 单文件零运维；足以承载状态机与审计 |
| DOCX 解析 | 标准库 `zipfile` + `xml.etree` | 直接解 OOXML，输出段落树 / 表格 / 页码 / 字符区间 |
| PDF 文本抽取 | **自研**（对象扫描 + `/Filter` 链 + ToUnicode CMap） | 零依赖；可精确定位字符区间；兼容交叉引用表与流两种写法 |
| 扫描件 OCR | Windows `Windows.Media.Ocr`（WinRT）／ Linux `tesseract` CLI | 复用系统能力，模型不随包分发；双后端按平台自动选择 |
| 图像处理 | 系统 OCR 自带预处理 + 自研文本规整 | 避免引入 Pillow/OpenCV；OCR 结果做 CJK 间隔空格规整 |
| 报告 PDF | Edge/Chrome 无头 `--print-to-pdf`，失败降级可打印 HTML | 系统自带；A4 打印样式；风险配色 `print-color-adjust: exact` |
| 规则引擎 | 自研 JSON 规则 + 5 种匹配模式 | 规则可读可改、非法务也能维护；不使用 `eval` 裸执行 |
| 大模型 | OpenAI 兼容 HTTP（`urllib`，显式禁用代理） | 与既有项目一致；**默认关闭**，仅润色措辞，不参与判定 |
| 定时/并发 | 标准库 `threading` + `queue`（v2.0 新增） | 保持零依赖 |
| 包管理 | **无**（零运行期依赖） | 老师交付约束「不带依赖、不含 venv」 |
| 构建期工具 | `python-docx` / `reportlab` / `pillow` / `pypdf` | **仅**用于生成示例合同集，已随交付物提供，运行不需要 |

### 3.1 关键设计判断（两条，继承自架构基线）

**判断一：风险判定走确定性规则，大模型只负责措辞。**

- 高/中/低风险结论 **100% 由规则引擎产出**，可复现、可解释、可复核、可审计；
- 大模型仅把命中的证据链改写成更自然的法律语言；
- 未配置 Key 或调用失败 → 自动回退内置示范条款模板库，界面明示当前模式。

理由：法务场景的结论必须能被质疑、被追溯、被复核。模型自由判断无法满足可审计要求。

**判断二：安全边界硬约束——只写评论。**

`writeback.py` **不存在**通过 / 拒绝 / 转交 / 撤回接口；审查意见固定包含边界声明
（仅供审批参考、不构成法律意见、最终结论由审批人作出）；大模型不触发任何审批动作。

## 五、核心数据模型（实测）

```sql
contract_cases      -- 审查任务（1 个审批单 = 1 条）
  id, case_no, title, applicant, send_dept, business_type,
  counterparty, credit_code, amount, currency, perform_period, effective_condition,
  source(approval|local), approval_instance, document_id, doc_sha256,
  review_status, writeback_status, risk_level, conclusion, blocked_reason,
  lawyer_opinion, created_at, updated_at
  UNIQUE(case_no)；索引：doc_sha256 / approval_instance

contract_documents  -- 合同文档与解析结果元信息
  id, case_id, filename, doc_type(docx|pdf|image), parse_engine, parse_status,
  parse_error, page_count, para_count, char_count, ocr_confidence, need_manual,
  sha256, file_path, text_path, created_at

review_results      -- 风险命中项（证据链）
  id, case_id, rule_id, rule_name, risk_level, clause_type, match_mode,
  evidence, page_no, para_index, char_start, char_end,
  reason, legal_basis, suggestion, suggestion_final, adopted, lawyer_note, created_at

writeback_logs      -- 回写记录
  id, case_id, mode(dry_run|live), channel, status, payload, comment_id, error, created_at

audit_logs          -- 全链路审计
  id, case_id, step, tool, status, detail, created_at
```

**溯源坐标系**：段落树落盘于 `data/parsed/case_{id}.json`；每段记录
`char_start/char_end`（指向全文扁平文本）、`page`、`para_index`。
风险命中绝对坐标 = `段落.char_start + 段内匹配偏移`，前端直接切片渲染高亮。
文字匹配先在原文匹配，失败则在**去间隔空格文本**上重试，并通过 `idx_map` 无损映射回原文坐标
（同时覆盖 PDF 逐字空格与 OCR 的 CJK 间隔空格）。

## 六、状态机（实测）

```
任务：  pending ──► parsing ──► reviewing ──► completed
                     │            │
                     └──► blocked ◄┘        blocked ──(重试)──► pending
回写：  not_written ──► writing ──► success
                          └─────► failed ──(重试)──► writing
```

阻塞判定：文档加密且无密码 → `blocked/ENCRYPTED`；OCR 置信度低于阈值或有效字符数不足 → `blocked/BLURRY`；
解析后正文为空或未抽取到文本层 → `blocked/EMPTY_BODY`。

## 七、规则模型（实测）

### 7.1 五种匹配模式

| 模式 | 语义 | 触发条件 |
| --- | --- | --- |
| `keyword` | 关键词包含 | 命中任一关键词子串 |
| `regex` | 正则匹配 | 命中任一条正则（原文或去空格文本） |
| `absence` | **必备条款缺失** | 所有正向表达式在**全文范围**内均不出现（避免条款标题段误报） |
| `pair` | **权责不对称配对** | 对我方不利的表达式与对方免责/封顶表达式**同时**命中，证据合并展示两侧原文 |
| `numeric` | **数值阈值** | 捕获数值并按 `gt/gte/lt/lte/eq` 与阈值比较 |

### 7.2 现行规则库规模（41 条）

| 合同类型 | 立场 | 规则数 | 高 | 中 | 低 |
| --- | --- | --- | --- | --- | --- |
| purchase 采购合同 | 本方为需方 | 12 | 5 | 5 | 2 |
| sales 销售合同 | 本方为供方 | 11 | 5 | 4 | 2 |
| service 服务合同 | 本方为委托方 | 9 | 4 | 4 | 1 |
| labor 劳动合同 | 本方为用人单位 | 9 | 4 | 4 | 1 |

### 7.3 判定优先级与阈值

**规则命中优先于大模型结论**；两者冲突时以规则为准并标注「规则/模型结论不一致，建议人工复核」。

```json
"review": { "reject_high_count": 2, "rectify_total": 1,
            "block_on_parse_fail": true, "min_text_chars": 30,
            "ocr_min_confidence": 0.5 }
```

## 九、安全边界、幂等与可观测（实测）

### 9.1 安全边界

- 只写评论；无通过/拒绝/转交/撤回能力；
- 意见文本固定含边界声明；
- 大模型不参与判定、不触发审批动作；
- 服务端强制上传大小上限（防超大文件打爆内存）；上传文件名做路径穿越硬化；
- 数据更新走字段白名单，未登记字段不拼 SQL 并写审计；
- HTTP 响应带 `X-Content-Type-Options: nosniff`、`Referrer-Policy: same-origin`、`Cache-Control: no-store`。

### 9.2 三级幂等

| 层级 | 幂等键 | 行为 |
| --- | --- | --- |
| 建任务 | 审批单号 `approval_instance` | 已建任务的审批单跳过 |
| 解析 | 文件 SHA256 `doc_sha256` | 指纹重复复用既有审查结果（阻塞态除外） |
| 回写 | `writeback_status` | `success` 状态重复回写直接跳过并记审计 |

### 9.3 可观测

审计覆盖 拉取 → 附件下载 → 指纹 → 解析（引擎/页数/段落/字符/OCR 置信度）→ 元数据 → 条款切分 →
规则审查（版本与命中编号）→ 摘要方式 → 回写（模式/通道/评论标识）；`/api/export` 一键导出全量 JSON。
当前实测审计日志 117 条。

## 十、附录 A · 可选生产化升级路径

V1.0 中列明的依赖栈不作废，作为**生产化升级路径**保留。以下为按优先级排序的改造路线：

| # | 当前形态（演示/内网） | 生产化目标 | 对应模块 | 前置条件 |
| --- | --- | --- | --- | --- |
| 1 | 单机 SQLite，单连接加锁 | PostgreSQL / MySQL，按 `approval_instance` 建唯一索引 | `app/store.py` | 引入 ORM 或连接池 |
