## R-04 技术方案 V1.0 承诺与实现的一致性 —— ❌ 重大偏离

**这是本次评审最核心的发现。** 技术方案 V1.0（第三节「技术选型与理由」、第四节「目录结构」）承诺的技术栈，
与实际交付的 v1.0 实现之间存在**系统性偏离**，共 9 项：

| # | 维度 | 技术方案 V1.0 承诺 | v1.0 实际实现 | 偏离性质 |
| --- | --- | --- | --- | --- |
| 1 | Web 框架 | FastAPI + Uvicorn ≥0.115 / ≥0.32 | 标准库 `http.server.ThreadingHTTPServer` | 全量替换 |
| 2 | 模板渲染 | Jinja2 ≥3.1 多页服务端渲染（SSR） | 静态 HTML + 原生 `fetch` 调接口（CSR） | 全量替换 |
| 3 | PDF 文本抽取 | PyMuPDF(fitz) ≥1.24 + pypdf ≥5.0 兜底 | 自实现对象扫描 + `/Filter` 链解码 + ToUnicode CMap 映射 | 自研替代 |
| 4 | 扫描件 OCR | RapidOCR(onnxruntime) ≥1.3（模型随包内置） | Windows 内置 `Windows.Media.Ocr`；Linux `tesseract` CLI | 换用系统能力 |
| 5 | 报告 PDF | reportlab ≥4.2 | Edge/Chrome 无头 `--print-to-pdf` | 换用系统能力 |
| 6 | 规则配置格式 | YAML（PyYAML ≥6.0.2） | JSON | 格式变更 |
| 7 | 包管理与依赖 | **uv 0.12.13** + `pyproject.toml` + `uv.lock`（13 个运行期依赖） | **无包管理、零运行期依赖** | 直接冲突 |
| 8 | 目录结构 | `app/{api,parsers,extractor,rules,llm}/` + `web/templates/*.html` + `data/rules/*.yaml` | `app/*.py`（扁平 11 模块）+ `ui/*.html` + `config/rules/*.json` | 结构重构 |
| 9 | 归一化全文 | 「剔除页眉页脚重复行」后生成 `full_text` | 统一段落树 + `char_start/char_end` 坐标系，**未实现页眉页脚剔除** | 承诺未落地 |

### 4.1 偏离的根因

两条要求在同一时间点相互冲突：

- **技术方案 V1.0**（D-09/D-12 授权启明决策）选择了「成熟生态栈」——FastAPI + Jinja2 + PyMuPDF + RapidOCR + reportlab + uv；
- **老师标注的交付物要求**（同批资产）明确「**不带依赖、不含 venv**」。

实现阶段选择了**服从交付物硬约束**，把整套技术栈替换为零依赖实现；但**技术方案 V1.0 未同步修订**，
导致「方案说 A、交付是 B」的文档性风险——一旦按方案 V1.0 评审交付物，会判定为"未按方案实现"。

### 4.2 偏离的实际影响评估

| 影响面 | 评估 |
| --- | --- |
| 功能完整性 | **无影响**。8 条验收标准 8/8 通过，33 项自检全通过 |
| 交付合规性 | **正面**。零依赖是老师要求的硬约束，技术方案 V1.0 反而与要求冲突 |
| 演示稳定性 | **正面**。无 CDN、无包安装、断网可跑，OCR 与 PDF 走系统能力 |
| 工程可维护性 | **混合**。自研 PDF 抽取器与规则引擎约 4,000 行需自行维护；但无依赖升级风险、无供应链风险 |
| 文档可信度 | **负面**。方案 V1.0 与交付物不一致，评审/答辩时无法自洽 |

### 4.3 评审裁定建议

> **以「零依赖可交付」为实现基线，将技术方案修订为 V2.0（方案对齐实现），
> 并把技术方案 V1.0 中列明的 13 个依赖栈作为"可选生产化路径"保留在附录。**

理由：① 零依赖是需求方（老师）的硬约束，不可放弃；② 1.0 实测证明该路线功能完整、验证充分；
③ 修订方案比推翻实现成本低一个数量级；④ 保留依赖栈作为生产化升级路径，答辩时可展示"技术判断力"。

## R-05 需求 2.4.2 角色权限落地 —— ❌ 未实现

需求 2.4.2 明确三类角色及权限边界：

| 需求角色 | 权限边界 | v1.0 现状 |
| --- | --- | --- |
| 法务审查人 | 查看详情、核对高亮证据、采纳/调整建议、补充意见并触发回写 | 能力已实现，但**任何访问者都能执行** |
| 业务经办人 | 提交审查申请、查看风险点与整改建议、下载报告 | 能力已实现，但**无身份区分** |
| 系统管理员 | 配置对接参数、维护规则与条款库、监控状态并处理阻塞重试 | 能力已实现，但**无权限隔离** |

**证据**：SPEC.md 第 10 节自述「无登录与权限隔离」；`app/` 全目录检索无 `role`/`login`/`session` 相关实现

**影响**：需求 2.4.2 是 2.4 节中**唯一未闭环的条目**。演示时无法体现"三角色分工"这一需求明确的业务设定，
也无法展示"越权拦截"这类答辩加分点。

**建议**：纳入 2.0，用标准库实现最小 RBAC（`http.server` + Cookie 会话 + 路由级权限表），不引入第三方框架。
